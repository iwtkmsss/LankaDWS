# LankaDWS — самодостатнє ТЗ на дизайн і frontend-реалізацію

## 0. Завдання для Codex і межі реалізації

Цей файл є source of truth для дизайну й frontend-реалізації; `lankadws-backend-spec.md` є парним source of truth для backend. Codex має створити **робочий responsive frontend LankaDWS**, а не landing page, набір скриншотів або статичну HTML-презентацію. Після запуску авторизований користувач одразу потрапляє в застосунок на `/overview`.

Стек проєкту зафіксований: **npm workspaces monorepo**, frontend — **React + Vite + TypeScript**, backend — **NestJS + TypeScript**, data layer — **Prisma ORM + SQLite**. Цей документ реалізує frontend у `apps/web` або в уже наявному еквівалентному workspace; backend регламентується окремим `lankadws-backend-spec.md`. Спільні DTO/enums/API contracts розміщуються в окремому workspace-пакеті на кшталт `packages/contracts`, але frontend не імпортує server-only код. Routing — browser history через React Router або сумісний наявний router. Стилі будуються на CSS variables/design tokens і перевикористовуваних компонентах; важкий готовий admin-template або UI-kit, який змінює погоджений вигляд, не використовується.

Якщо поруч передано `selected-dashboard-reference.png`, він є лише референсом щільності, темного sidebar і чистої enterprise-композиції. Не копіювати з нього назву, `PROTON`, старе меню, групові блоки або дані. Цей документ і останні погоджені правила мають вищий пріоритет за raster-reference.

Межі роботи:

- якщо Codex отримує лише цей файл — реалізувати frontend і mock data layer, backend у межах такого окремого завдання не писати;
- якщо поруч передано `lankadws-backend-spec.md` і поставлено завдання реалізувати весь monorepo — production mode працює через реальний NestJS API з того ТЗ, а mock provider залишається тільки для development/demo/testing за явним flag;
- mock service й real API client реалізують спільні typed repository/adapter interfaces; pages/components не знають, який provider активний;
- production build не fallback-иться мовчки на mock при недоступному API: показує bootstrap/offline/service state;
- створення, редагування, фільтри, drawers, погодження, сповіщення й основні стани мають реально працювати на mock/local state, а не бути декоративними кнопками;
- seed-data повинні містити щонайменше дві компанії, користувачів різних ролей, задачі, заявки, документи, події, статті, оголошення, contextual chat і audit events;
- для перевірки ролей передбачити dev-only перемикач demo-user або чотири mock-акаунти з нікнеймами `maria`, `andrii`, `olena`, `dmytro` для ролей `Працівник`, `Керівник`, `HR`, `Адміністратор`; mock-пароль/підказка можуть показуватися лише у dev-mode, у production-навігації такого перемикача й demo-credentials немає;
- усі переходи виконуються через реальні URL з підтримкою refresh, deep link, Back/Forward і відкриття посилання в новій вкладці;
- усі погоджені фото, portrait cutouts, error/empty-state illustrations потрібно **згенерувати як локальні статичні assets**, а не брати з випадкових URL;
- не вбудовувати назви, кнопки або службовий текст у raster-зображення: текст завжди залишається HTML;
- production build має завершуватися без TypeScript/build errors; ключові маршрути й responsive-стани перевіряються в браузері;
- у frontend-only mode інтеграція, що потребує backend, показує чесний mock-result через adapter і не імітує небезпечну операцію як реально виконану; у full-monorepo mode використовується реальний API result без mock fallback.

Коли цей файл використовується окремо, усі згадки `server-side`, API, cookies, jobs, malware scan, backup та audit retention нижче є контрактом майбутньої production-системи й вимогами до UI-станів, а не дозволом самовільно писати backend. Коли разом використовується `lankadws-backend-spec.md`, ці вимоги реалізуються backend-ом і перевіряються інтеграційно. Frontend demo не називається безпечним лише через приховані кнопки; mock auth/RBAC чітко відокремлюються від production security.

Порядок виконання для Codex:

1. Створити app shell, design tokens, шрифт Onest, routing і рольову навігацію.
2. Згенерувати та покласти в static/public директорію обов’язкові графічні assets із розділу 4.
3. Реалізувати сторінки й сценарії з розділів 6 і 11 на спільних компонентах.
4. Додати системні/error pages, permission states і URL-поведінку з розділів 5 і 9.
5. Перевірити desktop, tablet, mobile, keyboard flow, пряме відкриття URL і production build.

Суперечність тлумачиться на користь цього правила: **LankaDWS не має сутностей `Команда` або `Підрозділ`**. Працівники належать до компаній; керівник є роллю та/або явним погоджувачем, а не власником формальної команди.

## 1. Суть продукту

LankaDWS — внутрішній робочий простір для однієї або кількох пов’язаних компаній, у якому працівник бачить не всі можливі дані одразу, а те, що потребує його уваги зараз: найближчі події, прострочені задачі, власні заявки, рішення на погодження, оновлення документів і швидкі дії.

Попри назву CRM, продукт **не містить** клієнтів, лідів, угод, продажів, воронки, revenue, товарів, складу або зовнішнього customer portal. Це виключно внутрішня система для працівників, задач, заявок, календаря, документів, знань, доступів і адміністративних процесів.

Продукт не повинен виглядати як копія Bitrix, набір незалежних віджетів або звичайний admin template. Його характер — спокійний, точний і сучасний «операційний центр» із людяною фотографією, чіткою інформаційною ієрархією та мінімумом зайвих переходів.

Основна мова інтерфейсу — українська. Desktop — головна платформа; tablet і mobile мають підтримувати повсякденні сценарії без урізання критичних функцій.

## 2. Головна дизайн-ідея: Signal & Focus

В основі інтерфейсу три рівні інформації:

1. **Потребує уваги** — прострочення, запити на погодження, конфлікти у розкладі, нові згадки.
2. **Заплановано** — задачі та події, які мають конкретний час або дедлайн.
3. **Для контексту** — доступні оголошення, не термінові зміни у документах і події конкретної компанії.

На кожному екрані є одна очевидна головна дія, один домінантний інформаційний блок і другорядний контекст. Усі картки не повинні мати однакову візуальну вагу.

### Візуальний підпис продукту

- глибокий темно-синій sidebar;
- теплий світлий фон замість стерильного білого полотна;
- кобальтовий синій як primary accent;
- м’ятний колір тільки для живих позитивних статусів;
- тонкі сигнальні лінії та вузли, що продовжують геометрію фірмового знака LankaDWS;
- живі PNG-фото з прозорим фоном, частково інтегровані у картки;
- великі чисті заголовки й компактні робочі таблиці;
- легка асиметрія на dashboard, але строгий ритм на робочих екранах.

Сигнальна графіка не є окремою ілюстрацією на кожній сторінці. Вона з’являється тільки у welcome-блоці, error/empty states, onboarding і окремих брендованих поверхнях.

### Назва та wordmark

Офіційна назва продукту — **LankaDWS**. Слово `PROTON` може з’являтися лише в цій забороні або назві старого reference-файлу; у UI, generated assets, логотипі та user-facing документації воно не використовується.

Основне стилізоване написання логотипа — **LankaDWS**:

- `LankaDWS` — великий щільний wordmark;
- `/` — фірмовий кобальтовий акцент і графічний розділювач;
- `CRM` — менший uppercase із помітним міжлітерним інтервалом;
- слеш не є частиною офіційної назви та не використовується у звичайному тексті;
- у темному sidebar `LankaDWS` білий, `/` кобальтовий, `CRM` світло-блакитний;
- у світлій версії `LankaDWS` темно-синій, `/` кобальтовий, `CRM` muted-синій;
- абстрактний знак із трьох синіх смуг зберігається ліворуч від wordmark і візуально римується з літерою `E`.

### Типографіка

Основний шрифт — **Onest**. Це сучасний гібрид геометричного й гуманістичного grotesk із повною підтримкою української кирилиці, variable-вагою `100–900` та відкритою ліцензією SIL Open Font License 1.1. Шрифт дозволено self-host без залежності від зовнішнього CDN.

Onest використовується в усьому інтерфейсі, документах системи й auth-flow. Для робочого UI достатньо ваг `400`, `500`, `600` і `700`; надмірна кількість товщин не використовується. Wordmark `LankaDWS` залишається окремим фірмовим написанням і не збирається автоматично зі звичайного текстового стилю.

Для production використовуються self-hosted variable WOFF2 із потрібними latin/cyrillic subsets і системним sans-serif fallback. Onest не потребує штучного italic: акцент передається вагою, кольором і композицією. Офіційні джерела: [Google Fonts](https://fonts.google.com/specimen/Onest) та [upstream repository](https://github.com/simpals/onest).

Codex має покласти локальний variable WOFF2 та файл ліцензії у `public/fonts/` або еквівалентну static-директорію. Runtime-запитів до Google Fonts/CDN немає. Якщо репозиторій уже містить валідний Onest asset, дубль не створюється.

Оптимізація доставки шрифту:

- один variable WOFF2 замінює окремі файли `400`, `500`, `600` і `700`;
- завантажується лише мовний subset, потрібний початковій локалі; для українського інтерфейсу пріоритет має cyrillic-набір;
- критичний font-файл self-hosted і preload лише один раз; інші локалі не входять у початковий запит;
- використовується `font-display: swap` або еквівалентна стратегія без блокування тексту;
- системний fallback підбирається за близькими метриками, а line-height резервується наперед, щоб заміна шрифту не створювала layout shift;
- wordmark і логотип постачаються як оптимізований SVG/asset і не змушують завантажувати додаткову font-сім’ю.

### Геометрія та простір

- sidebar: 232 px у повному стані, 72 px у згорнутому;
- topbar: 68 px;
- desktop grid: 12 колонок, gap 20–24 px;
- основний відступ контенту: 28 px;
- card radius: 14 px для великих блоків, 10 px для компактних;
- button radius: 10 px;
- висота основної кнопки: 40 px;
- border: 1 px;
- тіні дуже легкі; у звичайному стані переважає border, а не shadow.

### Щільність і responsive-поведінка компонентів

- таблиці не використовують текст менше 13 px на desktop і 14 px на touch-пристроях;
- числа, час, суми й лічильники використовують tabular numerals;
- заголовок таблиці залишається sticky під topbar;
- повністю виконані або другорядні групи на складних екранах можна згортати;
- на ширині від 1440 px drawer може стискати контент, якщо ключові колонки залишаються читабельними;
- нижче 1440 px drawer відкривається поверх контенту з overlay і не руйнує таблицю;
- на екранах 1366×768 photo-focus переходить у компактний стан;
- центральна зона довгого sidebar прокручується, а профіль і системні пункти залишаються sticky внизу;
- критичні дії не залежать тільки від hover: вони доступні з клавіатури й на touch;
- споріднені списки можна об’єднувати на одній surface й розділяти лініями, щоб інтерфейс не перетворювався на сітку однакових bordered-карток.

### Progressive disclosure — поступове розкриття

Базове правило LankaDWS: **екран спочатку показує, що відбувається і що треба зробити далі, а не всю інформацію, яку система знає**. Мета — не механічно сховати рівно 50% контенту, а прибрати з постійного поля зору все, що потрібне рідко, не впливає на поточне рішення або дублює інші елементи.

Постійно видимі:

- назва й короткий контекст сутності;
- актуальний статус, блокер або дедлайн;
- відповідальний, якщо від нього залежить наступний крок;
- рівень конфіденційності, коли він важливий для дії;
- одна головна дія;
- незбережені зміни, помилка доступу або критичне попередження.

Відкриваються за запитом:

| Другорядна інформація | Патерн відкриття |
|---|---|
| Неактивні фільтри й сортування | Popover `Фільтри`; активні значення залишаються chips |
| Повні поля сутності | Context drawer |
| Історія, журнал і технічна metadata | Вкладка або accordion усередині drawer |
| Пояснення `Що це?` / `Як працює?` | Короткий popover через `?` |
| Особисті налаштування сторінки | Окремий settings drawer |
| Рідкісні розширені параметри | Accordion `Додаткові налаштування` |
| Bulk-actions | Toolbar тільки після вибору рядків |
| Небезпечні дії | Окрема нижня секція або secondary menu з поясненням наслідків |

Правила поведінки:

- drawer відкривається поверх контенту й не змінює ширини таблиці; виняток можливий лише на широкому екрані, якщо всі ключові колонки залишаються читабельними;
- після закриття зберігаються scroll position, фільтри, вкладка, сортування й вибраний рядок;
- фокус повертається на елемент, який відкрив drawer або popover;
- `Esc` закриває верхній некритичний шар; незбережені зміни спочатку отримують підтвердження;
- не використовувати вкладені drawers; складний drawer має локальні tabs або accordions;
- відкритий об’єкт може мати deep link без втрати контексту списку;
- на mobile drawer стає full-screen sheet із явною кнопкою повернення;
- критична дія не може бути доступна лише через hover, tooltip або приховане контекстне меню.

### Статуси

Кожний статус має системну комбінацію `текст + іконка + колір`. Колір не використовується як єдиний носій значення. Cobalt означає активний процес, mint — завершення, amber — очікування або блокер, coral — помилку чи прострочення, gray — неактивний або майбутній стан.

### Іконки

Один outline-набір із товщиною лінії 1.75–2 px. Не змішувати filled, 3D та outline-іконки. Колір іконки підказує дію, але статус завжди дублюється текстом або міткою.

## 4. Використання фото та PNG

Фото справді можуть зробити цей продукт значно дорожчим на вигляд, але тільки в місцях, де вони мають зміст.

### Де фото потрібні

1. **Welcome / Focus-блок dashboard.** Один прозорий PNG-виріз людини розташований праворуч і частково виходить за внутрішню сітку картки. Під і навколо фото — responsive CSS/SVG-шари cobalt і pale-blue; текст і кнопки залишаються ліворуч.
2. **Працівники.** Портрети є змістовним контентом довідника. Для списку використовуються квадратні crop-фото; у профілі — більший portrait. Це не групове фото й не візуалізація формальної команди.
3. **Login / onboarding.** Одне повноцінне editorial-фото робочого середовища з великою кількістю вільного простору.
4. **Error та empty states.** Окремі предметні PNG без тексту: відсутня сторінка, замок, розірваний signal, offline, порожня папка, календарний блок, стос документів. Вони мають виглядати як одна 3D/photographic-серія.

### Де великі фото не потрібні

- у таблиці задач;
- у календарній сітці;
- у звітах;
- у налаштуваннях;
- у кожній KPI-картці;
- як фон під дрібним робочим текстом.

### Стиль фотоконтенту

- природні люди, реальні пози й нормальне офісне світло;
- без рукостискань, постановочних нарад і «усі дивляться в камеру»;
- прохолодна нейтральна кольорокорекція;
- однаковий напрямок світла в усіх PNG-вирізах;
- не більше 1 великого photo-accent на одному екрані;
- критичний текст ніколи не вбудовується в raster-файл;
- люди на згенерованих фото є вигаданими й не повинні навмисно копіювати реальних співробітників;
- вихідні PNG з alpha зберігаються як master, а для продукту готуються оптимізовані WebP/AVIF-копії та оптимізований PNG fallback.

Текст і CTA завжди залишаються HTML, тому повторне використання не змінює зміст помилки.

Error/empty assets генеруються одним style family: м’який предметний 3D із матовими білими, pale-blue і cobalt поверхнями, однакова перспектива, світло зліва, прозорий фон, без тексту й персонажів. Не генерувати screenshot UI як raster asset.

### Доставка й бюджети зображень

Master-PNG зберігається як вихідний статичний asset. Браузер отримує responsive derivative або окремо оптимізований production-PNG, а не необроблений багатомегабайтний master.

Орієнтир щодо форматів і responsive delivery: [web.dev — Choose the right image format](https://web.dev/articles/choose-the-right-image-format).

- для raster-графіки порядок форматів: AVIF → WebP → PNG/JPEG fallback;
- derivative naming є передбачуваним: `hero-employee-maria-640.avif`, `-960.webp`, `-1400.png` або еквівалент, описаний в asset manifest;
- кожне велике зображення має responsive-варіанти щонайменше для mobile, tablet і desktop, а браузер отримує найближчий до фактичного розміру;
- photo-focus першого екрана завантажується пріоритетно й не позначається lazy;
- фото, обкладинки та empty-state нижче першого viewport завантажуються лише при наближенні до видимої області;
- `width`, `height` або aspect ratio відомі до завантаження, тому контент не стрибає;
- домінантний колір або легкий placeholder дозволений, але не замінює skeleton робочих даних;
- LCP-зображення має бути доступним браузеру без очікування складного JS і не ховатися лише в CSS background;
- приватні фото й документи використовують контрольований доступ і короткоживучі signed URLs; оптимізація не робить їх публічними.

Цільові бюджети для типового відображуваного розміру:

| Asset | Ціль | Максимум без окремого обґрунтування |
|---|---:|---:|
| Desktop photo-focus | до 250 KB | 450 KB |
| Mobile photo-focus | до 120 KB | 220 KB |
| Empty-state illustration | до 90 KB | 150 KB |
| Avatar 64×64 | до 15 KB | 25 KB |

Якість оцінюється в реальному компоненті на 1×/2× екранах. Автоматичне стискання не повинно створювати помітні контури навколо PNG-вирізів, ламати alpha або спотворювати обличчя.

### Мінімальний набір графічних assets

- 4 hero portrait cutouts, перелічені у контракті вище;
- `login-workspace.jpg` і responsive derivatives;
- 8–12 demo-аватарів не менше 512×512;
- 5 error-state і 4 empty-state PNG в одній серії;
- легкі ribbon/signal assets у SVG або PNG 2×, якщо їх неможливо якісно побудувати CSS;
- dark і light SVG-версії логотипу `LankaDWS`;
- manifest із filename, призначенням, intrinsic size, alt-policy та місцем використання.

## 5. Глобальна структура

### Організаційна модель

Одна інсталяція LankaDWS є tenant/workspace і може обслуговувати кілька юридичних або операційних компаній. Компанії є плоским переліком, а не деревом підрозділів.

- кожний працівник має одну основну компанію та за потреби доступ до додаткових компаній;
- задача, заявка, документ, подія, стаття або процес належать конкретній компанії чи мають явно позначений global-scope;
- поля `teamId`, `departmentId`, team lead і department tree не створюються;
- `Керівник` — роль і/або явний зв’язок `безпосередній погоджувач` у профілі працівника, а не вузол оргструктури;
- scope прав: `Власні`, `Обрані компанії`, `Усі компанії`; для окремих сутностей додатково працюють ACL, участь і роль у процесі;
- фільтр `Компанія` показується лише користувачам, які справді мають доступ більше ніж до однієї компанії;
- у URL, кеші, mock DTO й майбутніх API-запитах company-scope є явним; дані різних компаній не змішуються мовчки.

Масовий імпорт користувачів у MVP не реалізується й не повинен з’являтися як декоративна кнопка або фоновий job.

### Sidebar

Sidebar має один і той самий shell для всіх ролей: 232 px, однаковий wordmark, іконки, вертикальний ритм і sticky-профіль унизу. Спільні дозволені пункти ніколи не переставляються між ролями.

Базовий порядок:

1. Огляд
2. Завдання
3. Заявки
4. Календар
5. Документи
6. Працівники
7. Аналітика — лише за відповідним правом
8. База знань

Чат не займає окремий пункт: він відкривається з topbar або з контексту задачі, заявки чи документа. У нижній sticky-зоні: `Сповіщення`, `Налаштування`, avatar і підпис `Ім’я · Основна роль` на одному рядку. Наприклад: `Марія · Працівник`, `Андрій · Керівник`, `Дмитро · Адміністратор`. Якщо ролей декілька, у sidebar показується primary display role, а повний перелік — у profile popover. Довгий підпис має ellipsis і tooltip, але роль не зникає.

Системна роль `Адміністратор` за замовчуванням бачить у sidebar всі базові модулі та окремий parent-пункт `Адміністрування` із gear/shield-іконкою. Видимість модуля не дає автоматичного права читати його приватний контент: content permissions перевіряються окремо. У розгорнутому стані під parent показується вкладена навігація:

1. Користувачі
2. Компанії
3. Ролі та права
4. Безпека
5. Журнал дій
6. Система

Вкладені пункти з’єднані тонкою вертикальною лінією; активний child має маленьку cobalt-крапку й cobalt-текст. Parent залишається активним для всіх `/admin/*`. Сам parent веде на admin overview. Вкладена група згортана, але її стан не змінює доступи; на mobile вона відкривається всередині navigation drawer.

Активний пункт — світліший синій контейнер, а не проста синя смуга. Sidebar можна згорнути; tooltip показує назви пунктів. Порядок доступних пунктів не змінюється між ролями: приховуються лише недоступні модулі, а рольові відмінності реалізуються через dashboard, вкладки, badges і дозволені дії.

### Topbar

- breadcrumb або назва поточного розділу;
- компактний company-context selector лише для користувачів із доступом більше ніж до однієї компанії;
- глобальний пошук із підказкою `Пошук у LankaDWS…`;
- primary-кнопка `Створити` з рольовим меню типів: задача, заявка, подія, документ або оголошення;
- чат і сповіщення;
- компактний профіль.

`Ctrl/Cmd + K` відкриває command palette: перейти до розділу, знайти працівника, задачу, заявку, документ або статтю бази знань, створити дозволену сутність. Результати враховують company-scope й права.

#### Контекст компанії

Company selector не створює формальної команди й не є окремим workspace. Він визначає видимий company-scope поточного модуля:

- якщо доступна одна компанія, selector повністю прихований;
- якщо компаній декілька, показуються `Усі доступні` та конкретні дозволені компанії; `Усі доступні` відсутнє, якщо permission не дозволяє cross-company view;
- основна компанія є default при першому вході, але останній вибір запам’ятовується окремо для кожного модуля;
- на спискових routes вибір дублюється безпечним query-param `company=cmp_…` або `company=all`, тому refresh і shared deep link не змінюють scope мовчки;
- selector показується на `Завдання`, `Заявки`, `Календар`, `Документи`, `Працівники`, `Аналітика`, `Оголошення` та релевантних admin lists; у login, settings і standalone error shell його немає;
- entity deep link показує дозволену сутність незалежно від попереднього list-filter і завжди має видимий chip компанії;
- під час створення сутності поле `Компанія` є обов’язковим: поточна конкретна компанія підставляється автоматично, а зі scope `Усі доступні` користувач мусить обрати її явно;
- зміна selector скасовує застарілі запити, очищує selection/bulk state, оновлює URL і не показує cached rows іншої компанії;
- назва компанії не займає окрему постійну колонку на екранах, де scope вже однозначний; у режимі `Усі доступні` company label стає видимим у рядках.

### Context drawer

Задача, заявка, подія, документ, стаття, працівник або audit-запис відкриваються у правій панелі 420–480 px. Користувач не втрачає поточний список і фільтри. Drawer має власний deep link. Окрема повна сторінка потрібна тільки для складного процесу з великою кількістю кроків, наприклад onboarding/offboarding.

### URL, routing і browser history

Зміна активного розділу **завжди змінює URL**. Навігаційні елементи реалізуються як справжні links, а не як кнопки, що лише перемикають локальний state. Потрібні:

- Browser History API / browser router без `#` у URL;
- refresh на будь-якому дозволеному route без повернення на `/overview`;
- Back/Forward відновлюють сторінку, drawer, tab і безпечні фільтри;
- deep link можна скопіювати, відкрити у новій вкладці й передати іншому користувачу з відповідними правами;
- активний sidebar item і breadcrumb обчислюються з route, а не з окремого несинхронізованого state;
- кожний route має унікальний document title у форматі `Назва сторінки — LankaDWS`;
- після звичайного переходу focus переходить на `<main>`/H1, а scroll відновлюється передбачувано;
- deployment/server повертає application shell для відомих client routes, але asset/API paths не переписуються на HTML;
- базовий path конфігурується для deployment, але canonical routes нижче не змінюються без окремого рішення.

#### Канонічна карта маршрутів

| URL | Екран | Доступ / поведінка |
|---|---|---|
| `/` | Redirect | Після auth → `/overview`, без auth → `/login` |
| `/overview` | Особистий огляд | Усі авторизовані ролі; контент рольовий, але не груповий |
| `/tasks` | Завдання | Дозволений список |
| `/tasks/new` | Створення задачі | Modal/page state із власним URL |

| `/employees` | Працівники | Довідник із company filter за правом |
| `/employees/:employeeId` | Профіль працівника | Поля залежать від content-scope |
| `/analytics` | Аналітика | Лише за правом; company filter локальний |
| `/notifications` | Центр сповіщень | Tab через `?tab=action`; також `mentions`, `today`, `earlier` |
| `/messages` | Contextual chat surface | Відкривається з topbar, не з основного sidebar |
| `/messages/:threadId` | Конкретний діалог | Permission-checked deep link; safe title у document title |
| `/settings/profile` | Профіль | Особисті налаштування |

| `/login` | Вхід за нікнеймом і паролем | Public auth shell; email не приймається як ідентифікатор |
| `/first-login` | Обов’язкова заміна тимчасового пароля | Лише обмежена credential-change session; доступ до CRM ще не надано |

| `/access-help` | Допомога з доступом | Інструкція звернутися до адміністратора; без форми email-відновлення |
| `/session-expired` | Повторний вхід | Безпечний `returnTo` лише на внутрішній allowlisted path |

#### URL стан списків і drawers

- tab, search, sort, page/cursor, view і не sensitive filters зберігаються у query params: наприклад `/requests?tab=approval&company=cmp_2&status=pending`;
- приватний текст, нікнейм, email, пароль, тимчасовий credential, причина відсутності, токен, коментар або довільний user input у URL не записуються;
- відкриття рядка зі списку змінює path на `/:id`, але background location зберігає список; закриття drawer повертає точний попередній URL із filters;
- пряме відкриття `/:id` без background location показує той самий drawer поверх базового списку на desktop або повну detail surface на mobile;
- local tab drawer може використовувати `?panel=activity`, якщо це не розкриває приватних даних;
- після submit/створення використовувати replace/push усвідомлено: Back не повинен повторно відправляти форму;
- canonicalization прибирає невідомі query params і не допускає open redirect через `returnTo`;
- при відсутності доступу не можна на мить показувати cached content попереднього користувача або компанії.

## 6. Екрани

### 6.1 Огляд

Dashboard не копіює референс один в один. Він зберігає його зрозумілість, але має чіткішу ієрархію та фіксовані рольові варіанти. Користувач не збирає dashboard самостійно: система показує релевантний набір блоків відповідно до основної ролі та прав.

`Огляд` завжди є **особистим робочим екраном**. На ньому заборонені блоки з назвами або змістом `Команда сьогодні`, `Стан команди`, `Ризики команди`, `Навантаження команди`, `Пріоритети команди`, групова присутність чи рейтинг людей. Дані інших працівників з’являються лише в конкретній заявці, задачі, події або списку рішень, де користувач має роль.

#### Спільний перший ряд

**Focus-блок, 8 колонок, висота 168–190 px**

- персональне привітання;
- один короткий висновок про найважливіше на сьогодні;
- одна primary-дія;
- 2–3 компактні особисті метрики без окремих KPI-карток;
- один рольовий PNG-портрет праворуч;
- легка сигнальна графіка на фоні;
- можливість згорнути photo-частину для постійних користувачів;
- стан згортання запам’ятовується окремо для користувача;
- photo-частина не перевищує 40% ширини focus-блоку й не збільшує його висоту понад 190 px.

**Сьогодні, 4 колонки**

- наступна подія;
- вертикальна шкала 3–4 подій;
- all-day відсутності або важливі дедлайни;
- конфлікт часу виділяється окремою міткою.

#### Dashboard працівника

- `Потребує уваги`: прострочені задачі, повернуті заявки, документи для ознайомлення;
- `Мій день`: 3–6 активних задач із пов’язаною заявкою або документом;
- `Найближче`: особисті події й дедлайни;
- `Мої заявки`: статус останніх звернень;
- `Оголошення`: тільки релевантні основній/доступній компанії або ролі;
- швидкі дії: задача, заявка, подія, документ.

#### Dashboard керівника

- `Потребують рішення`: заявки та документи, де саме цей користувач є поточним погоджувачем; дія на dashboard — `Переглянути`, фінальне рішення приймається у drawer;
- `Мій день`: власні та призначені задачі;
- `Найближче`: особисті події й дедлайни;
- `Мої заявки`: власні звернення керівника як працівника;
- `Оголошення`: доступний контекст компаній;
- якщо є доступ до кількох компаній, filter `Усі компанії` розташовується всередині `Потребують рішення`, а не перетворює весь dashboard на керівницьку аналітику;
- швидкі дії: створити задачу, заявку, подію або документ.

#### Dashboard HR

- focus-блок використовує `hero-hr-olena` для demo-акаунта `olena`, а не випадковий портрет працівника чи групове фото;
- `Onboarding`: нові співробітники та прогрес підготовки;
- `Offboarding`: активні процеси й задачі, які прострочені;
- `Відсутності`: майбутні та непогоджені;
- `Ознайомлення`: хто не підтвердив важливі політики;
- `Документи співробітників`: записи, що потребують оновлення;
- `Події`: випробувальні терміни, річниці та заплановані HR-зустрічі.

HR-блоки можуть показувати записи різних працівників, бо це робоча черга конкретної ролі, але не називаються командними й завжди фільтруються за дозволеними компаніями.

Адміністратор не втрачає звичайний особистий `/overview`: він бачить там власні задачі, заявки й події як працівник. Системний overview відкривається окремо на `/admin`. Dashboard будь-якої ролі не повинен прокручуватися більше ніж на 1.5 desktop-екрана за стандартного набору даних.

### 6.2 Завдання

Головний робочий екран — **список**, а не kanban. Board і timeline доступні як перемикач виду.

Верхня зона:

- заголовок і кількість відкритих задач;
- primary `Нова задача`;
- сегменти `Мої`, `Створені мною`, `Усі доступні`, `Архів`; `Усі доступні` показується лише за розширеним правом;
- пошук і одна кнопка `Фільтри`; повний набір `Статус`, `Пріоритет`, `Дедлайн`, `Відповідальний`, `Компанія` відкривається у popover;
- активні фільтри показуються chips і скидаються одним кліком;
- збережені представлення: `Мій тиждень`, `Ризики`, `Без дедлайну`.

Таблиця:

- checkbox тільки для режиму bulk-action;
- назва й короткий контекст;
- компанія або короткий пов’язаний контекст;
- відповідальний з avatar;
- дедлайн;
- пріоритет;
- статус;
- індикатор коментарів/вкладень.

Drawer задачі:

- вкладка `Основне`: назва, опис, статус, пріоритет, дедлайн, відповідальний і checklist;
- зв’язки, залежності й спостерігачі згорнуті в окремі секції та показують короткий summary у заголовку;
- вкладка `Обговорення`: коментарі та вкладення;
- вкладка `Активність`: хронологія змін без технічного шуму;
- пов’язана заявка, документ, подія або onboarding-процес відкриваються deep link;
- sticky footer із `Зберегти` тільки коли є незбережені зміни.

У списку не показуються опис, checklist, останній коментар і повна історія. Індикатори коментарів, вкладень і залежностей лише повідомляють про їх наявність; зміст відкривається в drawer.

Повторювані задачі дозволені для регулярних внутрішніх процесів. Створення задачі з заявки, документа або повідомлення автоматично зберігає зворотне посилання на джерело.

### 6.3 Заявки та погодження

Заявки — єдина точка входу для внутрішніх звернень. Це не універсальний конструктор сутностей: адміністратор обирає та налаштовує тільки дозволені типи внутрішніх процесів.

Базові типи:

- відпустка, лікарняний або інша відсутність;
- доступ до системи, документа або внутрішнього ресурсу;
- технічна підтримка;
- обладнання;
- документ або довідка;
- витрати чи закупівля;
- звернення до HR;
- інша внутрішня заявка.

Верхня зона:

- заголовок і кількість активних заявок;
- primary `Нова заявка`;
- сегменти `Мої`, `На погодження`, `Компанія`, `Архів`; `Компанія` доступна лише користувачам із відповідним company-scope;
- пошук і кнопка `Фільтри`; `Тип`, `Статус`, `Пріоритет`, `Відповідальний`, `Строк` відкриваються у popover;
- активні фільтри залишаються компактними chips над списком;
- збережене представлення `Потребують рішення` для керівників.

Таблиця:

- номер і назва;
- тип;
- поточний відповідальний;
- статус;
- строк або SLA;
- дата оновлення.

Автор і поточний крок погодження не займають постійні колонки: короткий summary показується під назвою лише тоді, коли він впливає на наступну дію; повні дані доступні в drawer.

Статуси за замовчуванням: `Чернетка`, `Подано`, `На погодженні`, `Погоджено`, `У роботі`, `Повернуто`, `Виконано`, `Відхилено`, `Скасовано`.

Для заявок з автоматичними наслідками рішення та виконання зберігаються окремо:

- `Рішення`: очікується, погоджено, повернуто, відхилено, скасовано;
- `Виконання`: не розпочато, у черзі, виконується, завершено, часткова помилка, помилка.

Після позитивного рішення головний chip може показувати `Погоджено`, а вкладка `Результат` — стан кожної автоматичної дії. Збій календаря чи notification не відкочує вже зафіксоване рішення й не маскується статусом `Виконано`.

Drawer заявки:

- вкладка `Деталі`: номер, тип, автор, створено, коротка суть, поля конкретного типу, відповідальний і SLA;
- вкладка `Маршрут`: вертикальні кроки погодження, substitute та escalation;
- вкладка `Обговорення`: коментарі й вкладення;
- вкладка `Активність`: рішення та системні зміни;
- пов’язані задачі, події та документи згорнуті в секцію з лічильником;
- sticky action zone відповідно до ролі.

Дії погоджувача: `Погодити`, `Повернути на доопрацювання`, `Відхилити`, `Делегувати`. Головна позитивна дія одна; відхилення не повинно виглядати рівноцінною primary-кнопкою.

Фінальне погодження дозволене тільки після відкриття drawer і перегляду актуальної версії заявки. Для чутливих або фінансових типів рішення потребує короткого коментаря чи повторного підтвердження відповідно до політики.

Після рішення система виконує конкретний наслідок без універсального automation builder. Наприклад:

- погоджена відсутність з’являється в особистому календарі та планує privacy-safe статус присутності працівника;
- погоджений доступ створює задачу для IT;
- погоджене обладнання створює задачу відповідальному та запис у onboarding;
- запит документа створює пов’язану задачу й повертає готовий файл заявнику.

Користувач завжди бачить, хто зараз має прийняти рішення, коли завершиться строк і чому заявку повернули або відхилили.

### 6.4 Календар

- режими `День`, `Тиждень`, `Місяць`, `Розклад`;
- sticky mini-calendar ліворуч або у drawer;
- кольори означають тип події, а не конкретну людину;
- відсутності показуються окремою all-day смугою;
- права панель дня містить agenda, учасників і місце/посилання;
- drag-and-drop допустимий, але будь-яку зміну часу треба підтвердити toast-повідомленням з `Скасувати`.

### 6.5 Документи та база знань

Це два окремі основні routes і два sidebar-пункти: `/documents` та `/knowledge`. Вони використовують спільні file/ACL-компоненти, але перехід між ними завжди змінює URL.

#### Файли

Сегменти: `Мої`, `Доступні мені`, `Компанія`, `Останні`. `Компанія` показується лише за відповідним правом.

- list view за замовчуванням, grid — додатково;
- breadcrumb для папок;
- пошук усередині поточної папки або всього диска;
- колонки: назва, тип, власник, компанія, змінено, доступ;
- preview у drawer для PDF/зображень і metadata для інших форматів;
- upload-zone з чітким прогресом, помилкою та повтором;
- версії документа й журнал змін — у другій вкладці drawer;
- документ можна пов’язати із задачею, заявкою або onboarding/offboarding;
- документ може мати маршрут погодження та статус `Чернетка`, `На погодженні`, `Опубліковано`, `Архів`.

#### База знань

База знань призначена для інструкцій, регламентів, політик, FAQ та onboarding-матеріалів, а не для довільних файлів.

- категорії та дерево розділів;
- повнотекстовий пошук;
- стаття є головною читацькою поверхнею; автор і дата оновлення залишаються в компактному metadata-рядку;
- кнопка `Про документ` відкриває drawer із власником актуальності, версією, аудиторією, рівнем конфіденційності та датою наступного перегляду;
- чернетка, погодження, публікація, архів;
- історія версій і повний change log відкриваються у вкладці drawer; коротке `Що змінилося` можна розгорнути безпосередньо у статті;
- вкладення, пов’язані файли й задачі показуються згорнутими секціями з лічильниками;
- targeted visibility для обраних компаній, конкретних користувачів або ролей;
- позначка `Обов’язкове ознайомлення` з дедлайном;
- звіт, хто відкрив і хто підтвердив ознайомлення;
- дія `Повідомити про неточність` створює пов’язану заявку власнику статті.

Обов’язкове ознайомлення не займає постійну велику праву колонку. До підтвердження показується компактна sticky-панель унизу article area з дедлайном і однією кнопкою; після підтвердження вона перетворюється на невелику status-мітку. Навігація статті може згортатися на вузькому desktop і завжди стає drawer на tablet/mobile.

### 6.6 Працівники та життєвий цикл

Це найбільш photo-rich екран.

- заголовок `Працівники` без групової статистики й без оргдерева;
- пошук і фільтри за компанією, роллю, посадою, локацією та статусом;
- list view за замовчуванням і compact photo-grid як додатковий режим;
- картка працівника: портрет, ім’я, primary role, посада, компанія, privacy-safe статус, timezone і дві швидкі дії;
- hover не приховує критичну інформацію;
- профіль у drawer: великий портрет, дозволені контакти, компанія, прямий погоджувач/керівник, найближчі дозволені відсутності, кнопки `Написати` і `Поставити задачу`;
- каталог не показує причину відсутності, приватний HR-коментар або security metadata;
- відсутність формальної групи не заважає явно призначити погоджувача конкретному працівнику.

#### Onboarding

Onboarding відкривається як окремий workspace співробітника:

- фото, ім’я, посада, компанія, погоджувач/керівник і дата старту;
- загальний прогрес, але поруч обов’язково показується наступний крок;
- checklist, згрупований за `HR`, `IT`, `Керівник`, `Працівник`;
- кожен пункт є реальною задачею з відповідальним і дедлайном;
- залежності між кроками, наприклад створити акаунт до видачі доступів;
- обладнання, доступи, документи та обов’язкові матеріали;
- коментарі й загальна timeline;
- видимі блокери та прострочення;
- шаблони onboarding за компанією та/або посадою.

Повністю виконані групи автоматично згортаються, але залишаються доступними. За замовчуванням першими показуються блокери, прострочені й найближчі критичні кроки; дія `Показати всі` відкриває повний список.

#### Offboarding

- дата завершення роботи й відповідальний HR;
- передача активних задач і документів;
- повернення обладнання;
- завершення сесій і блокування доступів;
- фінальні документи;
- checklist для HR, IT і керівника;
- система не дозволяє завершити offboarding, доки критичні об’єкти не мають нового власника.

### 6.7 Контекстний чат

Чат відкривається з topbar або правої панелі конкретної сутності. Це легкий інструмент координації, а не окремий корпоративний месенджер.

- список особистих і контекстних діалогів;
- unread і mentions як різні стани;
- повідомлення можуть бути пов’язані із задачею, заявкою або документом;
- прикріплення файлу;
- reply і copy;
- дії `Створити задачу` та `Додати до заявки` з конкретного повідомлення;
- дата й статус доставки не мають візуально конкурувати з текстом;
- без відеодзвінків, stories, складної телефонії та зайвих реакцій у MVP.

### 6.8 Профіль і особисті налаштування

Особисті налаштування не змішуються з адмінкою й мають окремі routes:

- `/settings/profile`: ім’я, read-only `@нікнейм`, avatar, необов’язкові контакти, посада, primary company, timezone, locale; нікнейм, company і роль змінюються лише уповноваженим адміністратором;
- `/settings/notifications`: канали, digest, quiet mode і пріоритети;
- `/settings/security`: особиста зміна пароля з введенням чинного пароля, 2FA та recovery codes через re-auth; адміністративного reset тут немає;
- `/settings/sessions`: активні сесії та завершення інших сесій.

Profile popover у sidebar показує ім’я, primary role, company, переходи до цих routes і logout. У frontend-only demo рольовий перемикач доступний лише за development flag.

### 6.9 Аналітика

- період, компанія, тип процесу й відповідальний як локальні фільтри;
- верхній ряд — 3–4 KPI з попереднім періодом;
- графіки: виконання задач у часі, прострочення, SLA заявок і відсутності в агрегованому company-scope;
- внутрішні заявки: середній час відповіді, SLA, повернення на доопрацювання;
- погодження: середній час на кроці та поточні затримки;
- onboarding/offboarding: прогрес, прострочені кроки та типові блокери;
- база знань: актуальність статей і завершення обов’язкових ознайомлень;
- таблиця проблем під графіками дає перехід до конкретних сутностей;
- аналітика не повинна перетворюватися на приховане стеження за працівниками: за замовчуванням показуються процеси й агреговані показники;
- не використовувати 3D-графіки, pie chart із десятками сегментів і decorative numbers без пояснення;
- export доступний у меню, а не як велика головна кнопка.

### 6.10 Сповіщення та оголошення

#### Центр сповіщень

Центр сповіщень — один широкий робочий список без постійної правої колонки, статистичних карток і навчальних блоків.

- вкладки `Потребує дії`, `Згадки`, `Сьогодні`, `Раніше` мають лічильники й замінюють окрему статистику;
- погодження, повернуті заявки, блокери onboarding і обов’язкові ознайомлення завжди потрапляють у `Потребує дії`;
- пошук залишається видимим, а типи й джерела відкриваються через `Фільтри`; активні значення показуються chips;
- рядок містить іконку або avatar, назву, один безпечний рядок контексту, час, unread-стан і одну доречну дію;
- `Налаштування` відкриває right drawer із пріоритетами, тихим режимом, digest і каналами доставки;
- кнопка `?` відкриває короткий popover `Що потрапляє сюди`;
- `Позначити прочитаним` доступне у secondary menu й не приховує action-required записи;
- низькопріоритетні події можна об’єднати в щоденний digest;
- після закриття drawer зберігаються вкладка, scroll position, пошук і фільтри.

Не показувати на сторінці постійні блоки `Тихий режим`, `Що потрапляє сюди` або дубльовані числа `Сьогодні`: це інформація за запитом, а не щоденний контент.

#### Оголошення

Оголошення — короткий внутрішній контекст компанії, а не другий модуль документів або новинна соцмережа. Воно не має окремого пункту sidebar: користувач відкриває повний список із dashboard-блоку `Оголошення`, notification або command palette.

Список `/announcements`:

- спочатку показує одне pinned і непрочитані актуальні оголошення, потім інші за датою публікації;
- має company-context selector, пошук і compact filters `Непрочитані`, `Закріплені`, `Архів`;
- рядок/картка містить title, безпечний дворядковий preview, автора, company chips, publish date і pinned/unread state;
- прочитане оголошення стає спокійнішим візуально, але не зникає автоматично;
- dashboard показує максимум два актуальні оголошення й link `Усі оголошення`, щоб блок не витісняв особисті задачі.

Drawer `/announcements/:announcementId` показує title, body, автора, аудиторію у зрозумілому вигляді, час публікації, вкладення й пов’язані документи. Технічні audience IDs приховані. Відкриття ставить `readAt` як низькоризикову idempotent-дію; користувач може позначити оголошення непрочитаним.

Створення `/announcements/new` доступне лише за окремими permissions `announcements.create` і `announcements.publish`:

- поля: заголовок, короткий body, конкретні компанії, ролі та за потреби окремі користувачі;
- optional `Закріпити`, `Опублікувати зараз`, дата запланованої публікації та дата завершення показу;
- перед publish є audience preview з кількістю одержувачів і попередженням про користувачів без доступу до пов’язаного документа;
- статуси: `Чернетка`, `Заплановано`, `Опубліковано`, `Завершено`, `Архів`;
- редагування опублікованого оголошення створює зрозумілий audit diff; суттєва зміна може повторно позначити його непрочитаним лише після явного confirm;
- архівування прибирає оголошення з dashboard, але не видаляє audit і receipt metadata;
- оголошення не підтримує обов’язкове юридичне ознайомлення: для цього використовується документ або стаття бази знань із відповідним workflow.

Адміністрування категорій оголошень залишається у `/admin/system?tab=directories`; створення й публікація самого контенту не переносяться в системні налаштування.

### 6.11 Адміністрування

Адмін-панель — захищений режим усередині того самого LankaDWS shell, а не окремий шаблон і не суміш особистих налаштувань. Вона доступна тільки користувачам із відповідним правом.

Єдиною локальною навігацією адмінки є погоджена вкладена група в темному sidebar: `Користувачі`, `Компанії`, `Ролі та права`, `Безпека`, `Журнал дій`, `Система`. Друга світла nav-колонка або дубльовані top-tabs у workspace не створюються. Клік по parent `Адміністрування` веде на `/admin`.

У межах `/admin/system` дозволені локальні tabs `Процеси`, `Довідники`, `Сповіщення`, `Бренд`, `Фонові роботи`, оскільки це підрежими одного системного розділу, а не конкуренти sidebar-навігації.

#### Принципи адмінського UX

- кожна сторінка має одну головну дію;
- спочатку показувати проблеми та рішення, а не декоративні KPI;
- перед важливою зміною показувати, на скільки людей і об’єктів вона вплине;
- складні сутності відкривати у drawer, зберігаючи список і фільтри;
- не видаляти користувача, якщо достатньо деактивації;
- усі зміни ролей, доступів, безпеки й компаній потрапляють у журнал дій;
- за наявності незбережених змін знизу з’являється sticky-bar `Скасувати` / `Зберегти зміни`;
- небезпечні дії не ховати у випадкових іконках: вони мають пояснення наслідків і окреме підтвердження;
- один рольовий hero-PNG дозволений лише на `/admin`; на внутрішніх admin pages залишаються тільки аватари, іконки й preview фірмового оформлення;
- рідкісні пояснення, системна metadata та advanced-параметри відкриваються через `?`, drawer або accordion, а не займають постійну колонку;
- небезпечні можливості не маскуються, але їхні форми показуються лише після свідомого вибору відповідної дії.
- біля sticky-профілю завжди видно `Ім’я · Адміністратор`; це не замінює permission check.

#### 6.11.1 Огляд адміністратора

Огляд відповідає на три питання: що потребує дії, чи коректно налаштовані доступи та що нещодавно змінювали інші адміністратори.

Перший блок `Потребує дії`:

- облікові записи, для яких скоро спливе тимчасовий пароль або не завершено перший вхід;
- користувачі без ролі або основної компанії;
- запити на додатковий доступ;
- заявки без відповідального маршруту;
- прострочені кроки onboarding/offboarding;
- заблоковані входи або підозріла активність;
- об’єкти без нового власника після деактивації співробітника.

Другий блок `Стан системи`:

- активні, ті, що очікують першого входу, та деактивовані користувачі;
- кількість ролей і активних компаній;
- охоплення двофакторною автентифікацією;
- дата останньої перевірки прав.

Третій блок `Останні зміни` — компактний audit feed: хто, що змінив, з якою сутністю та коли. Поруч розташовані не більше трьох швидких дій: `Створити користувача`, `Додати компанію`, `Створити роль`.

Не показувати CPU, RAM, storage та uptime, якщо CRM не є інструментом технічного моніторингу.

#### 6.11.2 Користувачі

Верхня зона:

- заголовок і кількість активних користувачів;
- primary `Створити користувача`;
- пошук за ім’ям, нікнеймом і посадою;
- фільтри `Статус`, `Роль`, `Компанія`, `2FA`, `Остання активність`;
- збережене представлення `Потребують налаштування`.

Таблиця:

- користувач: avatar, ім’я, `@нікнейм`;
- статус: активний, очікує першого входу, призупинений, деактивований;
- основна компанія;
- роль;
- погоджувач/керівник, якщо заданий;
- остання активність;
- стан захисту: 2FA, активні сесії або попередження;
- контекстне меню без постійного набору небезпечних іконок.

Drawer користувача має вкладки `Профіль`, `Доступ`, `Життєвий цикл`, `Безпека`, `Активність`.

`Профіль`: ім’я, унікальний нікнейм, необов’язкові контакти, посада, основна компанія, додаткові дозволені компанії, погоджувач/керівник, timezone. Email, якщо його зберігають як контакт, не є логіном і не використовується для активації чи відновлення доступу.

`Доступ`: роль, company-scope, додаткові винятки та preview фактичних прав.

`Життєвий цикл`: onboarding/offboarding, обладнання, обов’язкові ознайомлення та відповідальні процеси.

`Безпека`: 2FA, активні сесії, останні входи, `Скинути пароль`, окрема дія `Скинути 2FA` за спеціальним правом і `Завершити всі сесії`.

`Активність`: останні адміністративно важливі дії користувача.

Створення нового користувача — короткий modal: ім’я, унікальний нікнейм, роль і основна компанія. Посада, контакти та додаткові компанії відкриваються в accordion лише за потреби. Primary-дія має назву `Створити обліковий запис`, а не `Надіслати запрошення`.

Після створення система показує нікнейм і криптографічно випадковий тимчасовий пароль лише один раз. Біля кожного значення є `Копіювати`, а над ними — попередження `Передайте дані працівнику через надійний канал`. Тимчасовий пароль не надсилається email, не потрапляє в URL, notification, analytics, client storage або audit log і після закриття result-screen не може бути переглянутий повторно. Якщо адміністратор закрив екран, доступна лише генерація нового тимчасового пароля. Статус акаунта до завершення сценарію — `Очікує першого входу`.

`Скинути пароль` — окрема критична дія з permission `users.credentials.reset`, недоступна звичайному менеджеру користувачів без цього права. Flow:

1. адміністратор повторно підтверджує власний пароль і, якщо налаштовано, 2FA;
2. бачить ім’я, `@нікнейм`, статус акаунта й наслідки, обирає дозволений офлайн-спосіб перевірки особи працівника та вводить обов’язкову причину;
3. підтверджує генерацію нового одноразового тимчасового пароля;
4. система негайно відкликає всі активні сесії цільового користувача та анулює попередні тимчасові паролі;
5. новий тимчасовий пароль показується адміністратору один раз із кнопкою `Копіювати` й строком дії;
6. користувач входить за нікнеймом і тимчасовим паролем, встановлює власний постійний пароль, після чого проходить звичайний вхід повторно.

Reset-dialog має два чіткі стани, а не довгу форму. У першому показано target, impact, спосіб перевірки особи та confirm. У другому — замаскований one-time secret із діями `Показати на 60 секунд` і `Копіювати`, строком дії та checkbox `Я зберіг дані для безпечної передачі`. Закриття попереджає, що повторний перегляд неможливий. Автоматичні QA-screenshots не створюються, доки secret розкритий; чинний або тимчасовий пароль не потрапляє у support attachment чи telemetry.

Адміністратор ніколи не може побачити чинний або новий постійний пароль користувача. Reset пароля не вимикає 2FA: втрата другого фактора обробляється окремою дією `Скинути 2FA` з окремим permission, повторною автентифікацією, причиною та audit-event. Власний пароль адміністратор змінює через особисті налаштування, а не через user drawer. Після наступного успішного входу користувач бачить in-app security notice про дату адміністративного reset і заклик повідомити відповідального, якщо він його не очікував; secret у повідомленні відсутній.

Reset пароля або 2FA іншому користувачу з повною системною роллю `Адміністратор` використовує two-person control, якщо в системі є другий активний повний адміністратор: перший створює короткоживучий запит, другий окремо re-authenticate-иться й підтверджує його, після чого one-time secret генерується для ініціатора. Одна людина не може бути і ініціатором, і погоджувачем. Якщо доступний лише один повний адміністратор, UI не обходить правило прихованою кнопкою — використовується задокументована backend break-glass CLI-процедура.

Заблокований через невдалі входи акаунт має окрему дію `Розблокувати доступ`, permission `users.security.unlock`, re-auth адміністратора, reason і audit-event. Розблокування не змінює пароль, 2FA, роль або сесії й не використовується як заміна reset.

Функція `Увійти як користувач` у LankaDWS відсутня. Адміністратор перевіряє доступ через `Перевірка доступу`, route preview і audit, не створюючи сесію від імені іншої людини.

Замість видалення використовується `Деактивувати`. Перед деактивацією система показує задачі, документи, активні погодження й процеси користувача та вимагає вибрати нового власника/погоджувача для критичних об’єктів.

Bulk-actions з’являються тільки після вибору рядків. Масова деактивація та зміна ролі завжди показують impact summary.

#### 6.11.3 Компанії

Route `/admin/companies` керує плоским переліком юридичних/операційних компаній без оргдерева.

Список показує:

- display name і юридичну назву;
- короткий code/slug;
- статус `Активна` або `Неактивна`;
- timezone і робочий календар;
- кількість активних користувачів;
- кількість записів, що потребують перенесення перед деактивацією.

Drawer компанії:

- назва, юридична назва, необов’язкові реєстраційні metadata без надлишкових полів;
- timezone, locale, робочі дні та календар свят;
- необов’язкові правила контактних даних; вони не впливають на вхід або відновлення доступу;
- default-погоджувачі/ролі для внутрішніх процесів;
- список користувачів через окремий lazy-loaded tab;
- журнал змін.

Компанії не вкладаються одна в одну. Деактивація не видаляє історію й дозволена лише після impact preview: активні користувачі, незавершені заявки, документи, календарні події та процеси мають бути завершені або перенесені. У списку є контрольований стан `Без основної компанії` для помилково налаштованих користувачів.

#### 6.11.4 Ролі й доступ

Це головний і найбільш відповідальний екран адмінки.

Ліва колонка містить список ролей:

- Адміністратор;
- Керівник;
- Працівник;
- HR;
- Перегляд;
- створені компанією custom roles.

Системні ролі можна переглядати та дублювати, але критичну основу ролі `Адміністратор` не можна випадково зруйнувати. Custom role має назву, опис, колірну мітку й кількість користувачів.

Центральна зона містить права, згруповані за доменами: `Завдання`, `Заявки`, `Календар`, `Документи`, `База знань`, `Оголошення`, `Працівники`, `Аналітика`, `Адміністрування`. За замовчуванням домени показуються компактними accordion-рядками з коротким summary на кшталт `3 права · Обрані компанії`; одночасно розгортається лише один домен.

Замість величезної матриці дрібних checkbox кожне право має зрозумілу дію і scope:

- `Немає`;
- `Власні`;
- `Обрані компанії`;
- `Усі компанії`.

Наприклад: `Переглядати документи — Обрані компанії`, `Редагувати документи — Власні`, `Керувати користувачами — Немає`.

Права з високим ризиком мають shield-позначку та коротке пояснення: керування ролями, журналом, безпекою, деактивацією користувачів, зміною нікнейма, `Скинути пароль`, `Скинути 2FA` й експортом даних. `Керувати користувачами` не надає автоматично `users.credentials.reset` або `users.mfa.reset`.

`Перевірка доступу` — унікальний контрольний інструмент, який відкривається окремою кнопкою у right drawer, а не займає постійну третю колонку. Адміністратор обирає користувача, компанію й тип об’єкта, після чого бачить фактичний результат: що людина може переглядати, створювати, змінювати або видаляти з урахуванням ролі, company-scope, ACL і індивідуальних винятків.

Рідкісні індивідуальні винятки, умови export і security-дозволи відкриваються через `Додаткові права`. Системні ролі у read-only режимі не показують sticky save bar.

Перед збереженням система показує diff:

- які права додано або забрано;
- скількох користувачів торкнеться зміна;
- які небезпечні можливості з’являться;
- чи не втратить система останнього повного адміністратора.

#### 6.11.5 Система: внутрішні процеси

Цей контент знаходиться у `/admin/system?tab=processes` і налаштовує тільки конкретні внутрішні workflow, а не довільні модулі CRM.

##### Типи заявок

- назва, іконка, короткий опис і категорія;
- хто може створювати;
- відповідальна роль, конкретний користувач або company-scope;
- строк реакції та виконання;
- невелика форма з дозволеними полями: короткий текст, великий текст, число, дата, список, користувач, файл;
- порядок полів і обов’язковість;
- доступність типу за роллю та компанією;
- preview форми перед публікацією.

##### Маршрути погодження

- послідовні кроки: прямий погоджувач користувача, HR, IT, фінанси, конкретна роль або конкретний користувач;
- паралельне погодження дозволене тільки для сценаріїв, де це справді потрібно;
- умови маршруту обмежені зрозумілими параметрами: тип заявки, сума, компанія, роль автора;
- строк кожного кроку й escalation-нагадування;
- preview маршруту для конкретного співробітника;
- захист від маршруту без фінального відповідального;
- версії: активні заявки завершуються за старим маршрутом, нові використовують опублікований.

##### Шаблони onboarding/offboarding

- назва, компанія та/або посада, для якої діє шаблон;
- групи `HR`, `IT`, `Керівник`, `Працівник`;
- задачі, відповідальні ролі, строки відносно дати старту або завершення;
- залежності між кроками;
- потрібні доступи, обладнання, документи та матеріали для ознайомлення;
- preview календаря процесу;
- версійність шаблону без зміни вже запущених процесів.

Наслідки погодження задаються з обмеженого безпечного списку: створити задачу, додати відсутність у календар, запланувати privacy-safe статус присутності працівника, повідомити роль, прикріпити готовий документ або запустити onboarding/offboarding.

##### Фонові роботи

Tab `/admin/system?tab=jobs` показує export, preview, scan, індексацію, notification і approval-effects:

- тип, пов’язану сутність, стан, прогрес/attempts і час оновлення;
- safe error code без приватного payload;
- `Повторити` лише для retryable job і з idempotency protection;
- `Відкрити сутність` через permission-checked deep link;
- фільтри `Стан`, `Тип`, `Компанія`, `Період`;
- correlation ID у detail drawer;
- bulk retry заборонений для небезпечних effects без окремого impact preview.

#### 6.11.6 Довідники

Це tab `/admin/system?tab=directories`. Локальні групи:

- статуси задач;
- пріоритети;
- статуси й категорії заявок;
- типи документів;
- типи відсутностей;
- категорії бази знань;
- категорії оголошень;
- причини деактивації;
- робочі локації.

Кожне значення має назву, необов’язковий колір, порядок, active/inactive та кількість використань. Значення можна reorder через drag handle. Якщо значення вже використовується, замість видалення пропонується деактивація або перенесення об’єктів на інше значення.

#### 6.11.7 Системні сповіщення

Це tab `/admin/system?tab=notifications`.

- категорії подій: задачі, заявки, погодження, документи, ознайомлення, оголошення, onboarding, календар, доступ, безпека;
- канали: in-app та необов’язковий email, якщо контактну пошту й поштовий adapter підключено; email ніколи не є каналом входу, активації або відновлення пароля;
- обов’язкові security-повідомлення не можна вимкнути;
- default rules можна задавати для ролі, але користувач може змінювати необов’язкові особисті налаштування;
- дія `Надіслати тестове сповіщення` показує preview тексту й каналу.

#### 6.11.8 Бренд

Це tab `/admin/system?tab=brand`.

- необов’язкова назва tenant/workspace; окремі компанії не змінюють тему застосунку;
- офіційна назва продукту `LankaDWS`;
- dark/light логотип;
- wordmark `LankaDWS`;
- primary color у дозволеному діапазоні контрасту;
- favicon;
- live preview sidebar, topbar, кнопки та login-екрана.

Це не повний конструктор тем. Адміністратор не може випадково змінити десятки відступів, шрифтів і кольорів статусів.

#### 6.11.9 Безпека

- вимога 2FA для обраних ролей або всіх користувачів;
- строк дії тимчасового пароля, за замовчуванням 24 години;
- перегляд конфліктів, заблокованих і невалідних нікнеймів; canonical-формат є системним правилом і не редагується довільно;
- максимальна тривалість сесії;
- завершення всіх сесій конкретного користувача;
- огляд невдалих входів і блокувань;
- SSO позначається як майбутня можливість, якщо його немає в MVP.

Зміна глобальної політики безпеки завжди показує кількість користувачів, яких вона торкнеться, і дату набуття чинності.

#### 6.11.10 Журнал дій

Audit log є незмінним для звичайного адміністратора.

Колонки:

- дата й час;
- виконавець;
- дія;
- сутність;
- результат;
- IP / пристрій, якщо ці дані збираються законно;
- кнопка відкриття деталей.

Фільтри: період, виконавець, категорія, дія, результат. У drawer запису показується before/after diff без технічного JSON за замовчуванням. Export розташований у secondary-меню та сам також фіксується в журналі.

#### Захист від помилок

- не дозволяти деактивувати власний акаунт або забрати у себе останнє повне admin-право;
- не дозволяти повторно використати нікнейм деактивованого або перейменованого акаунта; старе значення залишається reserved і не працює як login alias;
- зміна ролі самого себе потребує підтвердження іншим адміністратором, якщо це можливо;
- при конфлікті одночасного редагування показувати новішу версію та diff, а не мовчки перезаписувати;
- після безпечної зміни показувати toast із `Скасувати`, якщо операція реально оборотна;
- повторне підтвердження паролем або 2FA використовувати для критичних security-дій, якщо backend підтримує це;
- червона зона розміщується внизу drawer або сторінки й не є візуально головною до моменту свідомого відкриття.

#### Адаптивність адмінки

Desktop є основним режимом. На tablet уся sidebar-навігація, включно з admin children, стає компактним navigation drawer. На mobile дозволені перегляд стану, пошук користувача, блокування сесій і термінові безпекові дії. Редактор ролей, company-impact операції та bulk-actions відкривають read-only preview з рекомендацією завершити зміну на ширшому екрані.

## 7. Авторизація, безпека та конфіденційність

Безпека є частиною продуктового UX, а не лише backend-реалізацією. Інтерфейс завжди пояснює користувачу, чому потрібне повторне підтвердження, чому доступ обмежено й які наслідки матиме критична дія.

### 7.1 Екрани авторизації

Обов’язковий набір:

- вхід **лише за нікнеймом і паролем**;
- перший вхід із тимчасовим паролем;
- обов’язкова заміна тимчасового пароля на власний;
- налаштування 2FA;
- введення одноразового коду;
- показ recovery codes один раз із підтвердженням збереження;
- сторінка допомоги `Зверніться до адміністратора` без email-форми;
- адміністративне скидання пароля без email;
- пароль успішно змінено;
- сесія завершилася;
- акаунт тимчасово заблокований;
- акаунт деактивований;
- повторна автентифікація перед критичною дією.

Екран входу використовує LankaDWS wordmark, одну editorial-фотографію або PNG-композицію й компактну форму. Фото не конкурує з формою та приховується на mobile. У формі рівно два поля: `Нікнейм` і `Пароль`, checkbox `Показати пароль`, primary `Увійти` та secondary-link `Не можете увійти?`. Поля `Email`, `Компанія` або `Роль` на login-екрані відсутні. Помилка нейтральна: `Нікнейм або пароль неправильні`; вона не підтверджує існування облікового запису.

Нікнейм є окремим login identifier, а не display name:

- унікальний без урахування регістру в межах усього tenant/workspace, оскільки один акаунт може мати доступ до кількох компаній;
- canonical-формат — 3–32 символи, латинські літери `a–z`, цифри, крапка, дефіс або underscore, без пробілів; зберігається lowercase;
- `dmytro`, `dmytro.k`, `dmytro_2` — валідні приклади; email-адреса не приймається навіть тоді, коли збігається з контактною поштою;
- ім’я працівника може бути українською й змінюється незалежно від нікнейма;
- зміна нікнейма доступна лише за окремим permission, потребує re-auth, показує impact, відкликає активні сесії та фіксується в audit log;
- нікнейм деактивованого користувача й попередній нікнейм після перейменування залишаються зарезервованими та не можуть бути видані іншій людині; старе значення не працює як login alias.

#### Перший вхід і тимчасовий пароль

Тимчасовий пароль генерується системою, має не менше 20 випадкових символів, діє за замовчуванням 24 години, анулюється після успішного використання або повторного reset і ніколи не дає доступу до робочих даних напряму. Після правильної пари `нікнейм + тимчасовий пароль` backend видає лише коротку обмежену credential-change session і переводить на `/first-login`.

На `/first-login` користувач двічі вводить власний постійний пароль. Після успішної зміни тимчасова session завершується, показується `/password-changed`, а користувач входить повторно через `/login` уже з новим паролем; повна сесія не створюється автоматично. Якщо для ролі обов’язковий 2FA, його setup/challenge виконується до доступу до `/overview`. Якщо тимчасовий пароль прострочений або втрачений, `/access-help` пояснює, як зв’язатися з адміністратором, без self-service email recovery.

Recovery codes є лише резервним способом пройти другий фактор після правильного нікнейма й постійного пароля. Вони не замінюють пароль і не є self-service password recovery.

Постійний пароль:

- мінімум 15 символів, якщо пароль може бути єдиним фактором; якщо 2FA обов’язковий для всіх входів, мінімум може бути 8, але UI заохочує довгі passphrase;
- підтримує щонайменше 64 символи, пробіли, вставлення з password manager й `autocomplete`;
- перевіряється за blocklist поширених, скомпрометованих і контекстних значень, зокрема похідних від `LankaDWS` та нікнейма;
- не вимагає штучної комбінації uppercase/lowercase/цифри/символу й не змінюється примусово за календарем без ознак компрометації;
- ніколи не зберігається або не повертається у відкритому вигляді; UI не має функції `Показати поточний пароль`.

Адміністративне скидання є recovery-процесом LankaDWS. Публічної форми `Введіть email/нікнейм для відновлення` немає. Backend приймає reset лише від активної сесії з `users.credentials.reset`, після re-auth/2FA; створює одноразовий тимчасовий пароль, відкликає сесії користувача й записує actor, target, причину, час і результат без самого secret. Для останнього доступного повного адміністратора production має окрему задокументовану break-glass процедуру на рівні власника інсталяції; вона не реалізується як прихована кнопка у frontend.

Парольна політика й reset-flow мають бути звірені з актуальними [NIST SP 800-63B](https://pages.nist.gov/800-63-4/sp800-63b.html), [OWASP Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html) та [OWASP Forgot Password Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html). Вимога власника продукту про відсутність email-recovery реалізується через контрольований offline/admin-assisted recovery, а не через слабкі security questions.

### 7.2 Сесії та обліковий запис

- користувач бачить активні сесії: пристрій, браузер, приблизна локація, остання активність;
- можна завершити одну або всі інші сесії;
- після адміністративного reset пароля всі старі сесії цільового користувача відкликаються обов’язково; після звичайної особистої зміни користувач може завершити всі інші сесії;
- idle timeout і максимальна тривалість сесії задаються політикою;
- критичні зміни ролей, безпеки, export і доступ до особливо чутливих даних можуть вимагати повторного пароля/2FA;
- повідомлення про новий вхід не містить приватного контенту;
- відключення 2FA потребує повторної автентифікації та фіксується в audit log.

Технічна реалізація повинна використовувати захищені cookies або еквівалентну безпечну модель сесій, захист від CSRF, rotation/revocation токенів, rate limiting входу та сучасне стійке salted-хешування паролів. Нікнейми порівнюються в canonical lowercase, але password не нормалізується непередбачувано. Авторизаційні рішення завжди приймає server-side.

### 7.3 Права доступу

- default deny: відсутнє право означає відсутній доступ;
- прихована кнопка не є захистом; кожна операція перевіряється backend;
- scope записів: `Власні`, `Обрані компанії`, `Усі компанії`; ACL і роль у процесі можуть додатково звужувати доступ;
- окремі права на перегляд, створення, зміну, погодження, export, архівування й адміністрування;
- окремі права на конфіденційні поля заявки або профілю;
- `Керувати системою` не дорівнює `Читати весь контент`;
- адміністратор бачить конфігурацію компаній, акаунтів, metadata й системні налаштування, але приватні чати, HR-документи й конфіденційні заявки — тільки за окремим правом;
- зміна прав набуває чинності без затримки для нових запитів і відкликає заборонені активні дії;
- global search, notifications, analytics, export і direct links застосовують ті самі правила доступу.

### 7.4 Рівні конфіденційності

| Рівень | Приклад | Видимість за замовчуванням |
|---|---|---|
| Загальний | Оголошення, опублікована інструкція | Обрані компанії або всі доступні компанії |
| Внутрішній | Задача, робочий документ | Учасники, ACL або дозволена компанія |
| Конфіденційний | Фінансова заявка, обмежений документ | Автор, погоджувачі, визначені ролі |
| HR / Security | Причина відсутності, особистий документ, security-event | HR/security та явно уповноважені особи |

Доступний календар або каталог працівників може показувати `Працівник відсутній`, але не причину лікарняного/відпустки. Notification preview, email, dashboard, search snippet, URL і activity feed ніколи не розкривають більше, ніж дозволено поточному користувачу.

### 7.5 Файли та вкладення

- allowlist типів і граничний розмір файлу;
- перевірка фактичного MIME, а не лише розширення;
- очищення небезпечних назв;
- malware scanning до відкриття файлу іншим користувачем;
- quarantine state із зрозумілим повідомленням;
- файли не зберігаються у публічно доступній директорії;
- доступ до перегляду й завантаження перевіряється на кожний запит;
- тимчасові signed links мають короткий строк дії;
- небезпечні формати не відкриваються inline;
- preview сторонніх документів ізолюється від основного застосунку;
- завантаження, export і перегляд конфіденційного файлу можуть фіксуватися в журналі.

### 7.6 Цілісність погоджень

- автор не погоджує власну заявку, якщо політика явно не дозволяє виняток;
- погоджувач бачить точну версію даних, за яку голосує;
- зміна ключових полів після рішення скидає або повторно запускає погодження;
- повторний click чи повтор HTTP-запиту не створює дубль події, задачі або рішення;
- делегування не створює циклічний маршрут;
- відхилення і повернення вимагають причини;
- відсутній погоджувач автоматично замінюється визначеним substitute або заявка переходить у контрольовану escalation-чергу;
- примусове завершення адміністратором потребує причини, повторної автентифікації та окремого audit-event.

### 7.7 Audit, retention і відновлення

Audit log фіксує:

- входи, невдалі входи, 2FA та session-events;
- створення облікового запису, зміну нікнейма, адміністративний reset пароля й reset 2FA без запису самих secret;
- зміни ролей і прав;
- створення, погодження, відхилення, делегування та примусове завершення;
- export;
- перегляд особливо конфіденційного контенту, якщо це передбачено політикою;
- деактивацію користувачів і передачу власності;
- зміни security settings та внутрішніх процесів.

Для журналу визначаються строк зберігання, доступні ролі та процедура export. Записи не редагуються через звичайний інтерфейс. Резервні копії мають шифруватися, перевірятися відновленням і зберігатися окремо від основної системи.

#### Базова retention-політика

Це стартові product defaults, а не юридична порада. Перед production вони підтверджуються власником системи відповідно до договорів і локальних вимог. Зменшення строку не видаляє дані миттєво без impact preview.

| Категорія | Default retention | Поведінка після строку |
|---|---:|---|
| Активні задачі, заявки, onboarding/offboarding | Поки активні | Не видаляються автоматично |
| Архівні задачі, заявки й process records | 5 років після архівування | Контрольований purge або anonymization за policy |
| Опубліковані документи та їхні версії | 7 років після заміни/архівування | Видалення лише після dependency і legal-hold check |
| Покинуті неопубліковані document/article drafts | 180 днів без активності | Попередження власнику, потім контрольоване очищення |
| Статті бази знань та оголошення | 3 роки після архівування | Metadata/audit можуть зберігатися довше |
| Contextual chat і звичайні коментарі | 2 роки після останньої активності | Purge body/attachments за policy, збереження мінімального audit reference |
| In-app notifications | 180 днів | Автоматичне очищення; action-required не раніше завершення пов’язаної дії |
| Audit подій доступу, ролей, credentials і export | 5 років | Append-only archive або purge за затвердженою policy |
| Інші application/audit events | 3 роки | Контрольоване очищення |
| Завершені session records і login metadata | 180 днів | Видалення або агрегація без точних device/IP details |
| Тимчасовий пароль і reset result | Не зберігається у відкритому вигляді | One-time result зникає одразу після закриття/expiry |
| Готовий export-файл | 24 години | Файл видаляється, job metadata залишається 180 днів |
| Background-job payload/error detail | 30 днів | Залишається safe metadata і correlation ID до 180 днів |
| Локальна offline-чернетка | До 30 днів неактивності | Очищається після warning; негайно на logout/deactivation для sensitive data |

Legal hold або розслідування призупиняє purge лише для явно позначених records і фіксується в audit. Retention job працює batch-ами, має dry-run/impact report для адміністратора, idempotency, retry і не блокує API. Звичайний адміністратор не може мовчки скоротити строки, очистити audit або зняти legal hold без окремого permission і re-auth.

## 8. Матриця доступів

Матриця нижче визначає default-поведінку. Реальний доступ формується роллю, дозволеними компаніями, ACL, роллю у конкретному процесі й додатковими permission sets. Прямі винятки для користувача використовуються лише за потреби й завжди аудіюються.

| Розділ | Працівник | Керівник | HR | Адміністратор | Перегляд |
|---|---|---|---|---|---|
| Огляд | Особистий | Особистий + власна черга рішень | Особистий + дозволені HR-черги | Системний; бізнес-контент лише за окремим правом | Дозволені особисті блоки |
| Завдання | Власні й призначені | Власні, призначені та дозволені company records | HR-задачі у дозволених компаніях | Metadata; контент за окремим правом | Дозволені read-only |
| Заявки | Власні | Власні та на погодження | Дозволені HR-категорії | Налаштування маршрутів; вміст за окремим правом | Немає |
| Календар | Власний і явно доступні події | Власний і події за ACL/company-scope | Відсутності й HR-події | Налаштування; події за окремим правом | Дозволені події |
| Документи | За ACL | За ACL/company-scope | HR-категорії | Налаштування; вміст за ACL | Опубліковані за ACL |
| База знань | Читання доступного | Читання/авторство | HR-матеріали | Категорії й workflow; контент за ACL | Опубліковані статті |
| Оголошення | Читання своєї аудиторії | Читання; створення лише за окремим правом | Читання/публікація у дозволених компаніях за правом | Налаштування категорій; publish лише за content-правом | Читання своєї аудиторії |
| Працівники | Дозволений каталог | Каталог дозволених компаній; приватні поля приховані | Lifecycle у дозволених компаніях | Акаунти й metadata; приватний контент за окремим правом | Дозволений каталог |
| Аналітика | Особиста за наявності модуля | Агрегована за дозволеними компаніями | HR-аналітика | Системна; бізнес-аналітика за правом | Немає або read-only |
| Адміністрування | Немає | Немає | Лише делеговані HR-налаштування | Повне системне керування | Немає |

### Критичні дії

| Дія | Додаткова перевірка | Audit | Відновлення |
|---|---|---|---|
| Змінити роль або права | Re-auth/2FA, impact preview | Обов’язково | Через попередню версію |
| Переглянути HR/security-контент | Окреме право, інколи причина доступу | За політикою обов’язково | Не застосовується |
| Export даних | Окреме право, re-auth для чутливого export | Обов’язково | Файл має обмежений строк доступу |
| Деактивувати користувача | Impact summary, передача власності | Обов’язково | Реактивація без повернення старих сесій |
| Скинути пароль користувачу | Окреме право, re-auth/2FA адміністратора, причина, one-time secret | Обов’язково, але без пароля | Новий reset анулює попередній тимчасовий пароль |
| Скинути 2FA користувачу | Окреме право, re-auth/2FA адміністратора, причина | Обов’язково | Повторне налаштування 2FA при наступному вході |
| Reset credentials повному адміністратору | Two-person control або backend break-glass, якщо іншого admin немає | Обов’язково для обох actor | Новий контрольований reset |
| Розблокувати акаунт | `users.security.unlock`, re-auth, причина | Обов’язково | Повторне блокування за security policy |
| Погодити заявку | Drawer, актуальна версія, за потреби 2FA | Обов’язково | Лише контрольоване скасування |
| Завершити всі сесії | Confirm, re-auth для чужого акаунта | Обов’язково | Новий вхід |
| Видалити/архівувати документ | Перевірка залежностей і retention | Обов’язково | Відновлення до завершення retention |

### Тимчасове делегування

Керівник/погоджувач може призначити substitute на визначений період. Делегування має дату початку й завершення, company-scope, обсяг дій і причину. Воно не передає зайві права, не дозволяє змінювати ролі та відображається у журналі. Після завершення строку доступ відкликається автоматично.

## 9. Системні стани та крайові сценарії

Для кожного ключового екрана дизайнер готує не лише filled-state.

| Стан | Поведінка |
|---|---|
| Loading | Skeleton повторює реальну геометрію, кнопки не стрибають |
| Empty | Пояснення, чому порожньо, і одна доречна дія |
| No results | Збережені фільтри не губляться, доступне `Скинути фільтри` |
| Partial error | Працюючі блоки залишаються, помилковий блок можна повторити |
| Full error | Людське пояснення, код для підтримки, `Спробувати ще раз` |
| Offline | Незбережена чернетка не губиться, показується стан синхронізації |
| No access / 403 | Причина без розкриття приватних даних, повернення або запит доступу, якщо дозволено |
| Not found / 404 | Пошук або повернення до попереднього контексту |
| Session expired | Збереження безпечної чернетки та повернення після входу |
| Stale data | Попередження, оновлення даних без втрати введених змін |
| Edit conflict | Порівняння версій і свідомий вибір, без silent overwrite |
| Maintenance | Короткий статус і очікуваний час лише якщо він відомий |
| Quarantined file | Файл недоступний до завершення перевірки, дозволена заміна |
| Background job | Видимий стан `У черзі / Виконується / Готово / Помилка`, можна залишити сторінку |
| Partial automation | Людське рішення збережене; кожний effect має власний статус, idempotent retry й escalation |

### 9.1 Повноцінні error та service pages

Error pages є обов’язковими routes/components, а не лише toast. Вони використовують LankaDWS wordmark, Onest, світлий canvas, один локальний PNG із `public/assets/errors/` і максимум одну primary-дію. Stack trace, database message, token, повний URL із secret/query або технічний payload користувачу не показуються.

| Стан | Коли показується | UI й основні дії | URL / status |
|---|---|---|---|
| 401 Session expired | Сесія закінчилась або відкликана | `Сеанс завершено`, пояснення про безпечну чернетку, primary `Увійти знову` | `/session-expired?returnTo=...`; після login повернення лише на allowlisted internal path |
| 403 Forbidden | Route існує, але роль не має доступу до модуля/дії | `У вас немає доступу`, primary `До огляду`, secondary `Назад`; optional `Запросити доступ`, якщо workflow існує | Відомий URL зберігається; сервер/API повертає 403 |
| Privacy-preserving 404 | Об’єкт конфіденційний або не можна підтвердити його існування | Та сама нейтральна 404 без згадки, що об’єкт існує | Початковий URL зберігається; 404 |
| 404 Not found | Невідомий route, видалений або неправильний id/slug | `Такої сторінки немає`, короткий global search, primary `До огляду`, secondary `Назад` | Catch-all не redirect-ить на `/404`; зберігає введений URL і повертає 404, де hosting це підтримує |
| 409 Conflict | Версія змінилася під час редагування | Diff, `Оновити дані`, `Скопіювати мої зміни`; без silent overwrite | Зазвичай modal/full state на поточному entity route, не окрема постійна сторінка |
| 410 Gone / expired one-time resource | Одноразове службове посилання, export або тимчасовий credential більше не чинні | `Ці дані більше не діють`, primary `Звернутися до адміністратора` або `До входу` | Поточний route; token/secret не логувати й не повторювати в UI |
| 429 Rate limited | Забагато повторів входу, search або export | Людський cooldown, disabled retry до дозволеного часу | Поточний route; не видавати внутрішні ліміти |
| 500 Internal error | Route/API не може безпечно продовжити | `Не вдалося завантажити сторінку`, correlation/reference code, primary `Спробувати ще раз`, secondary `До огляду` | Поточний URL; 500 на server error |
| 503 Maintenance | Планові роботи або сервіс тимчасово недоступний | `LankaDWS тимчасово недоступна`, `Повторити`; ETA тільки якщо достовірний | Standalone service shell; 503 + `Retry-After`, якщо відомо |
| Offline | Немає мережі | `Немає з’єднання`, стан локальної чернетки, `Перевірити знову`; автоматична ненав’язлива перевірка | Поточний route з offline state; `/errors/offline` лише для preview/test |
| App bootstrap failure | Не завантажився authenticated shell | Мінімальна standalone-сторінка без залежності від основного chunk, `Оновити` | Поточний URL; не нескінченний spinner |

Правила shell:

- при 403/404 усередині валідної сесії sidebar і topbar можна зберегти, якщо вони вже безпечно завантажені; приватний previous content прибирається;
- при bootstrap failure, maintenance, login/first-login error використовується автономний branded shell без sidebar;
- 500 окремого widget не повинен падінням знищувати всю сторінку: component error boundary залишає інші дозволені блоки працездатними;
- кожна error page має H1, короткий опис, keyboard focus на H1, document title і `noindex`;
- `Назад` використовує history лише коли є безпечний same-origin entry; інакше веде на `/overview`;
- retry не створює дубль mutation і показує pending-state;
- correlation ID короткий, copyable і не містить приватних даних;
- error analytics фіксує route pattern, build version і correlation ID, але не повний sensitive URL або form values;
- generated illustrations декоративні (`alt=""`); зміст помилки передається HTML-текстом;
- у development доступна preview-галерея `/errors/403`, `/errors/404`, `/errors/500`, `/errors/offline`, `/errors/maintenance`; у production ці demo-links не показуються в навігації.

## 10. Нефункціональні вимоги

### 10.1 Продуктивність

Performance перевіряється не лише лабораторно, а й на p75 реальних сесій окремо для desktop і mobile/tablet.

| Метрика | Ціль |
|---|---:|
| LCP | не більше 2.5 s на p75 |
| INP | не більше 200 ms на p75 |
| CLS | не більше 0.1 на p75 |
| Локальний feedback після click/keypress | до 100 ms |
| Перехід до вже завантаженого розділу | контент до 500 ms |
| Відкриття drawer із валідного кешу | до 200 ms |
| Основні поля drawer із мережі | до 800 ms на p75; skeleton з’являється одразу |
| Перші результати global search | до 1 s на p75 |

Порогові значення LCP, INP і CLS відповідають офіційним рекомендаціям [Core Web Vitals](https://web.dev/articles/vitals) і перевіряються на 75-му перцентилі.

Додаткові budgets:

- початковий JavaScript для authenticated shell та активного route — ціль до 250 KB у стисненому вигляді; перевищення потребує окремого обґрунтування;
- критичний CSS активного route — ціль до 60 KB у стисненому вигляді;
- third-party JavaScript за замовчуванням не підключається; кожна залежність має довести користь, вплив на bundle, privacy і можливість lazy-load;
- main-thread tasks довші за 50 ms розбиваються або переносяться з критичного interaction path;
- CI попереджає про перевищення budget і блокує непояснене погіршення ключової метрики більш ніж на 10%;
- великі списки використовують server-side search/filter/sort і cursor або page pagination;
- інтерфейс не рендерить сотні невидимих рядків: довгі списки застосовують pagination, windowing або virtualization;
- зображення доставляються у відповідному розмірі, а master-PNG не використовується як production-файл;
- drawer не завантажує маршрут, вкладення, коментарі й audit до відкриття відповідної вкладки.

### 10.2 Надійність даних

- чернетки заявок, статей і складних форм autosave локально або server-side;
- незбережені зміни захищені navigation guard;
- повторний запит не дублює погодження, задачу, подію чи notification;
- побічні дії погодження виконуються транзакційно або мають контрольоване відновлення;
- тимчасова втрата мережі не очищує форму;
- конфлікти версій показують diff;
- архівування використовується замість фізичного видалення там, де потрібна історія;
- усі дати зберігаються в UTC і показуються у timezone користувача.

### 10.3 Резервне копіювання та відновлення

- цільовий RPO — не більше 1 години для робочих даних;
- цільовий RTO — не більше 4 годин для критичної внутрішньої системи;
- backup шифрується й ізольований від основного середовища;
- процедура відновлення перевіряється регулярно, а результат документується;
- окремо перевіряється відновлення metadata, файлів і audit log.

### 10.4 Спостережуваність

- structured application logs без паролів, токенів і приватного вмісту;
- error tracking із correlation ID;
- Real User Monitoring для LCP, INP і CLS за route, device class і версією релізу без запису приватного контенту;
- метрики frontend long tasks, route-load, drawer-load, bundle size і failed resource;
- backend p50/p75/p95 latency, error rate, slow queries, query count, cache hit ratio, queue delay/failures, notification delivery і backup status;
- performance dashboard порівнює поточний реліз із попереднім і виділяє regression понад затверджений budget;
- health checks не відображаються звичайному працівнику як декоративні dashboard-графіки;
- критичні збої внутрішніх процесів мають alert для технічного адміністратора.

### 10.5 Сумісність

- підтримуються актуальні стабільні версії Chrome/Edge, Firefox і Safari;
- інтерфейс перевіряється на 1920×1080, 1440×900, 1366×768, tablet і mobile;
- zoom 200% не приховує критичні дії;
- складні desktop-редактори на mobile переходять у read-only або спрощений безпечний режим із поясненням.

### 10.6 Безпека застосунку

- централізована валідація вхідних даних;
- захист від XSS, CSRF, injection, brute force і небезпечного upload;
- Content Security Policy та базові security headers;
- secrets не зберігаються у frontend-коді або репозиторії;
- окремі середовища development, staging і production;
- dependency scanning та регулярне оновлення критичних залежностей;
- security events не містять зайвих персональних даних.

### 10.7 Progressive loading і frontend delivery

Progressive disclosure у дизайні напряму визначає архітектуру завантаження: **прихований контент не завантажується, доки користувач не відкрив відповідний рівень**.

Загальний підхід відповідає принципам [lazy loading і code splitting у MDN](https://developer.mozilla.org/en-US/docs/Web/Performance/Guides/Lazy_loading), але конкретні межі та security-правила визначаються цим ТЗ.

| Момент | Завантажується | Не завантажується |
|---|---|---|
| Вхід у розділ | App shell, фактична навігація за правами, counts активних tabs, видимі рядки й потрібні довідники | Drawer, невідкриті tabs, історія, вкладення, повні профілі |
| Hover/focus рядка | За можливості — легкий prefetch основних полів після короткої затримки | Коментарі, audit, файли, чутливі поля без права |
| Відкриття drawer | Основні поля сутності та дозволені дії | Дані невідкритих локальних tabs |
| Відкриття tab/accordion | Дані конкретної вкладки або секції | Решта прихованих секцій |
| Повторне відкриття | Валідний кеш показується одразу й тихо перевіряється актуальність | Повний повтор усіх запитів без потреби |
| Export / великий звіт | Створення background job і статус виконання | Формування великого файлу в request-response циклі |

Frontend-вимоги:

- route-level code splitting: `Аналітика`, `Адміністрування`, складний календар, редактор ролей і editors не входять у bundle dashboard;
- важкі charts, document preview, rich-text editor і diff viewer підключаються лише на екрані, де потрібні;
- prefetch запускається лише після наміру користувача — hover, keyboard focus або наближення посилання до viewport — і не обходить permission check;
- prefetch вимикається або обмежується на повільному чи економному з’єднанні;
- однакові паралельні запити deduplicate, застарілий search/request скасовується;
- пошук використовує debounce приблизно 250–350 ms, але keyboard navigation і локальна фільтрація вже отриманого малого набору залишаються миттєвими;
- під час revalidation попередні дозволені дані не зникають: показується компактний стан `Оновлюємо`;
- mutation оновлює або invalidates конкретну сутність, залежні counts і відповідний рядок, а не очищує весь application cache;
- skeleton відповідає геометрії саме того рівня, який завантажується, тому відкриття drawer не блокує весь список.

### 10.8 Кешування та актуальність

- versioned static assets із content hash мають довгий immutable cache;
- довідники, іконки категорій і незмінні metadata можуть використовувати stale-while-revalidate;
- кеш робочих сутностей ізольований щонайменше за company/tenant, користувачем, permission scope, entity id і версією;
- server-side authorization виконується перед поверненням навіть кешованого результату;
- зміна ролі, company-scope, індивідуального права, ACL або рівня конфіденційності негайно invalidates пов’язаний permission/data cache;
- HR/Security-відповіді, recovery codes, session details і особливо чутливі файли не потрапляють у shared cache; для них використовується `no-store` або еквівалентна політика;
- ETag/version або еквівалент дозволяє не передавати незмінений payload повторно;
- browser cache не є джерелом істини для прав, погоджень і критичних статусів;
- offline/local draft шифрує або не зберігає чутливі поля відповідно до політики; після повернення мережі користувач бачить стан синхронізації;
- logout, деактивація або завершення сесії очищує приватний client cache.

### 10.9 API-контракт, запити й фонові роботи

У frontend-only реалізації цей розділ відтворюється typed mock service і видимими UI-станами. Реальний backend не входить у поточний deliverable.

- list endpoint повертає лише поля, потрібні таблиці; detail, comments, route, attachments і audit мають окремі контрольовані запити;
- filtering, sorting, permission scope і pagination виконуються server-side;
- майбутні API/індекси мають враховувати tenant і company разом зі status, assignee, deadline та updated_at; frontend mock DTO вже використовує `companyId`, а не `departmentId`/`teamId`;
- забороняється N+1 для avatar, відповідального, статусу, counts і ролей; застосовуються batch/preload-підходи;
- API підтримує field projection або окремі компактні DTO для list, drawer summary і full detail;
- важкі export, PDF/preview, malware scan, масові notification і перерахунок аналітики виконуються у queue; bulk user import у MVP відсутній;
- background job має статус `У черзі`, `Виконується`, `Готово`, `Помилка`, retry policy і correlation ID;
- після готовності export/звіту користувач отримує in-app notification; файл має контрольований строк доступу;
- повторний запуск job або request використовує idempotency key і не створює дубль;
- агрегована аналітика за великий період готується наперед або інкрементально, а не перераховується повністю на кожне відкриття;
- rate limit, queue limits і backpressure захищають систему від масових export, search і notification;
- повільні запити мають query budget, журналюються без приватного payload і потрапляють у performance review.

### 10.10 Межі безпечної оптимізації

Optimistic UI дозволений тільки для легко оборотних і низькоризикових дій, наприклад `прочитано/не прочитано`, pin або персональне представлення. Помилка має повертати попередній стан і пояснювати причину.

Optimistic UI не використовується для:

- погодження, відхилення або делегування заявки;
- зміни ролі, прав, security policy чи confidentiality;
- деактивації користувача й завершення чужих сесій;
- HR-рішень, offboarding і передачі власності;
- результату malware scan або зняття файлу з quarantine;
- фінального підтвердження обов’язкового ознайомлення.

Оптимізація не може прибрати server-side permission check, CSRF/XSS-захист, audit, version conflict, accessibility semantics або підтвердження ризикової дії. Якщо кеш і сервер не збігаються, перемагає актуальний server state, а інтерфейс пояснює зміну без silent overwrite.

## 11. Основні сценарії

### Створення задачі

`Створити` → `Задачу` → компактний modal із назвою, відповідальним, дедлайном і необов’язковим зв’язком із заявкою/документом/подією → `Створити`. Після цього відкривається drawer для необов’язкових деталей. Швидке створення не повинно змушувати заповнювати 12 полів.

### Робота з простроченням

Запис з’являється у `Потребує уваги` → клік відкриває drawer → користувач змінює дедлайн або завершує задачу → елемент зникає з черги з короткою анімацією та можливістю `Скасувати`.

### Запит на відсутність

Це еталонний наскрізний flow LankaDWS, за яким перевіряються progressive disclosure, права, версійність, погодження, mobile і автоматичні наслідки.

Приклад: **Марія Іваненко**, дизайнер, подає відпустку на **20–24 травня 2026**, заміна — **Марко Литвин**, погоджувач — безпосередній керівник **Андрій Коваль**. Для звичайної п’ятиденної відпустки маршрут містить одне рішення керівника; HR отримує доступ за своєю роллю та notification відповідно до політики, але не створює зайвий крок.

#### Передумови

- профіль Марії активний, має основну компанію, timezone і явно визначеного погоджувача/керівника;
- тип заявки `Відсутність · Відпустка` опублікований і має чинну версію маршруту;
- політика визначає робочі/вихідні дні, дозволені строки, потрібність заміни й обов’язкові автоматичні дії;
- Андрій має фактичне право погоджувати заявки Марії у відповідній компанії;
- календар і presence-status service доступні або можуть прийняти idempotent background job.

Якщо критична передумова відсутня, чернетка зберігається, але система не створює заявку з «нічийним» маршрутом.

#### Ролі та видимість

| Роль | Бачить | Не бачить / не може |
|---|---|---|
| Автор Марія | Власні поля, приватний HR-коментар, маршрут, SLA, рішення та результат | Чужі HR-дані, внутрішні security-поля |
| Керівник Андрій | Компанію, період, тривалість, заміну, доступність заміни, дозволені перетини календаря, актуальну версію | Приватний HR-коментар і поля поза його content-scope |
| HR | Дозволені HR-поля, політику відсутності, результат і audit у своєму scope | Security-вміст без окремого права |
| Марко та організатори подій | Безпечне повідомлення про відсутність і потрібну заміну | Причину, приватний коментар, маршрут і службову timeline |
| Системний адміністратор | Конфігурацію маршруту, metadata job і технічний стан | Приватний HR-вміст без окремого content-права |

Календар компанії або дозволений каталог працівників може показати `Марія Іваненко відсутня`, але не причину чи приватний коментар.

#### Крок 1. Дані й чернетка

`Створити` → `Заявку` → `Відсутність` → `Відпустка`.

Обов’язкові поля:

- дата початку й завершення;
- тип відсутності;
- заміна, якщо цього вимагає політика.

Необов’язковий `Приватний коментар для HR` є окремою згорнутою секцією з lock-позначкою. Він не входить у manager payload, preview, notification або search snippet.

Форма:

- autosave з часом останнього успішного збереження;
- перевіряє порядок дат, робочі дні, свята й дубль активної відсутності;
- після зміни дат із debounce показує кількість робочих днів, доступність обраної заміни й кількість подій, що перетинаються;
- не завантажує повний список подій, доки користувач не натисне `Переглянути`;
- попереджає про недоступність заміни; policy визначає, це warning чи blocker.

#### Крок 2. Перевірка перед надсиланням

Окремий review-state показує:

- тип, період, тривалість і заміну;
- `2 події перетинаються` та `Заміна доступна на весь період`;
- хто погоджує й очікуваний строк рішення;
- що система зробить після погодження: особистий календар, статус присутності працівника, сповіщення;
- collapsed приватний HR-коментар;
- одну primary-дію `Надіслати заявку`.

Review не дублює повну форму. `Назад` повертає до редагування без втрати даних.

#### Крок 3. Надсилання й маршрут

Перед створенням server-side повторно перевіряє поля, право автора, чинну policy й маршрут.

- один submit створює одну заявку через idempotency key;
- snapshot полів отримує версію `v1`;
- статус переходить `Чернетка → Подано → На погодженні`;
- фіксуються route version, поточний погоджувач і SLA;
- після успішного створення URL переходить із `/requests/new?type=absence` на `/requests/:requestId` через replace, тому Back не повторює submit;
- Андрій отримує privacy-safe notification у `Потребує дії`;
- Марія бачить `Хто вирішує`, `До якого часу` й посилання на власну заявку;
- notification не містить приватний HR-коментар.

Offline-submit не відправляється мовчки у фонову чергу: заявка залишається чернеткою зі зрозумілим станом і явним повтором після відновлення мережі.

#### Крок 4. Рішення керівника

Андрій відкриває заявку з `На погодження` або notification. Drawer завантажує основні поля `v1`; `Маршрут`, `Обговорення` й `Активність` завантажуються лише після відкриття відповідної вкладки.

До рішення видно:

- автора, компанію, період, тривалість і заміну;
- доступність заміни, перетини подій і критичні дедлайни;
- короткий preview автоматичних наслідків;
- `Актуальна версія · v1`;
- повідомлення `Приватні HR-поля приховано`;
- факт, що рішення потрапить в audit.

Дії:

- `Погодити` — єдина primary;
- `Повернути` — вимагає коментаря, що саме уточнити;
- `Відхилити` — secondary/danger action із причиною;
- `Делегувати` — у secondary menu, лише дозволеному substitute без циклу й розширення прав.

Звичайна відпустка не потребує повторного 2FA. Re-auth застосовується лише якщо конкретна policy або тип даних позначає рішення як чутливе.

Якщо заявку змінено, скасовано або право Андрія відкликано після відкриття drawer, server відхиляє старе рішення, показує новий стан і не виконує автоматичних наслідків.

#### Крок 5. Погодження й автоматичний результат

Позитивне рішення записується атомарно з version check, actor, timestamp і audit-record. Після цього створюється idempotent execution job.

Для відпустки система:

1. створює all-day подію `Відсутність` у календарі Марії;
2. планує privacy-safe статус присутності Марії `Відсутня` на 20–24 травня;
3. повідомляє Марію, Марка й дозволених організаторів двох подій;
4. створює взаємні deep links між заявкою, календарем і presence-record.

Кожен effect має окремий ключ `request + version + effect type`, тому retry не створює дубль календарної події або notification.

Вкладка `Результат` показує:

- `Подію додано в календар`;
- `Статус присутності заплановано`;
- `Учасників повідомлено`;
- компактну timeline `Надіслано → Погоджено → Автоматичні дії завершено`;
- посилання `Відкрити календар` і згорнуті `Пов’язані об’єкти`.

Calendar і presence status є обов’язковими effects. Їхній збій залишає рішення `Погоджено`, але `Виконання` переходить у `Часткова помилка` або `Помилка`; заявка не показує повний статус `Виконано`. Notification retry не вимагає повторного погодження.

#### Версійність і повернення

Після `Повернути`:

- заявка має статус `Повернуто`, а коментар керівника видимий автору;
- Марія редагує дані без зміни snapshot `v1`;
- повторне надсилання створює `v2` і новий approval attempt;
- Андрій бачить короткий diff `Що змінилося`;
- рішення за `v1` не можна застосувати до `v2`;
- route повторно перевіряється за policy, але історія попередньої спроби не видаляється.

Автор може скасувати заявку до завершення рішення, якщо policy не забороняє. Скасування invalidates pending action і повідомляє поточного погоджувача.

#### Переходи flow

| Поточний стан | Подія | Наступний стан | Що бачить користувач |
|---|---|---|---|
| Чернетка | Надіслати | Подано → На погодженні | Поточний погоджувач і SLA |
| На погодженні | Повернути з коментарем | Повернуто | Причина й `Уточнити заявку` |
| Повернуто | Надіслати зміни | На погодженні, нова версія | `v2` і diff |
| На погодженні | Відхилити | Відхилено | Причина та audit timeline |
| На погодженні | Погодити | Погоджено + Виконання у черзі | Result-state із прогресом effects |
| Погоджено | Усі mandatory effects успішні | Виконано | Посилання на календар і status |
| Погоджено | Частина effects неуспішна | Часткова помилка | Який effect не готовий і стан retry |
| Чернетка/На погодженні | Скасувати автором | Скасовано | Хто й коли скасував |

#### Error та edge states

| Сценарій | Поведінка |
|---|---|
| Немає керівника або маршруту | Чернетка збережена; submit заблокований із людським поясненням і routing alert адміністратору |
| Події перетинаються | Warning і `Переглянути`; blocker лише якщо так визначає policy |
| Заміна недоступна | Запропонувати іншу людину; не скидати дати й коментар |
| Подвійний click/retry submit | Повертається та сама заявка, без дубля |
| Drawer містить застарілу версію | Рішення блокується, показується diff і `Оновити` |
| Сесію завершено під час редагування | Безпечна чернетка зберігається; після входу користувач повертається до review |
| Offline під час submit | Немає фальшивого success; явний retry після повернення мережі |
| Право погоджувача відкликано | 403 без приватних деталей, action invalidated, маршрут перераховується контрольовано |
| Андрій недоступний | Активується тимчасовий substitute або escalation за policy, без циклічного делегування |
| Заявку скасовано в іншій сесії | Drawer оновлюється; кнопки рішення стають недоступними |
| Calendar/presence effect не спрацював | Рішення лишається погодженим; failed effect отримує idempotent retry й alert після ліміту |
| Notification не доставлено | Фіксується failure/retry; приватні дані не додаються у fallback-канал |
| Різні timezone/святкові календарі | Дати зберігаються нормалізовано, а тривалість рахується за policy компанії й timezone автора |

#### Mobile

- desktop drawer стає full-screen sheet;
- таблиця заявок не відображається під ним;
- tabs можуть прокручуватися горизонтально, але `Деталі` й status залишаються видимими;
- sticky footer має touch targets не менше 44×44 px і безпечний відступ від системної зони;
- `Повернути` й `Погодити` залишаються видимими; `Делегувати` переходить у overflow menu;
- права, version check, audit і business logic ідентичні desktop.

#### Performance і data loading

- review завантажує summary та counts перетинів; повні події — лише після `Переглянути`;
- manager list отримує компактний DTO без приватних HR-полів;
- drawer отримує detail payload; route, discussion, activity та attachments мають окремі запити;
- після рішення invalidates рядок, tab counts, author request і пов’язані календарні/status queries;
- result-state може показувати job progress без блокування списку;
- desktop і mobile використовують ті самі endpoints і permission rules.

#### Критерії приймання flow

- Марія створює й надсилає заявку без повторного введення даних;
- review до submit показує період, тривалість, доступність заміни, погоджувача й наслідки;
- приватний HR-коментар не потрапляє Андрію, Марку, календарю, notification або search;
- подвійний submit створює рівно одну заявку `v1`;
- Андрій не може погодити невідкриту або застарілу версію;
- повернення вимагає зрозумілого коментаря, а повторне надсилання створює `v2` із diff;
- звичайне погодження не створює зайвий 2FA-step;
- після погодження calendar, presence status і notifications мають окремі видимі результати;
- retry failed effect не створює дубль календарної події, status або notification;
- partial failure не змінює рішення на `Відхилено` і не показує фальшиве `Виконано`;
- календар компанії та каталог працівників не розкривають причину відсутності;
- author і approver бачать одну спільну audit timeline у межах своїх прав;
- offline, session-expired, stale-version і revoked-permission не призводять до втрати чернетки чи неконтрольованого рішення;
- mobile дозволяє переглянути актуальні дані й прийняти рішення без horizontal scroll;
- список, drawer і невідкриті tabs відповідають progressive-loading правилам розділу 10.7.

### Внутрішня IT-заявка

Співробітник обирає `Технічна підтримка`, описує проблему та додає скриншот → система призначає IT-відповідального й SLA → IT створює пов’язану задачу або одразу відповідає → автор підтверджує вирішення → заявка переходить у `Виконано`.

### Погодження документа

Автор завантажує нову версію документа → відправляє на погодження → погоджувач бачить зміни й коментар → погоджує або повертає на доопрацювання → після погодження версія стає опублікованою → цільові працівники отримують ознайомлення, якщо воно обов’язкове.

### Запуск onboarding

HR створює профіль майбутнього співробітника, задає компанію, посаду, погоджувача/керівника й дату старту → система застосовує відповідний шаблон → створює реальні задачі для HR, IT, керівника і співробітника → dashboard показує прогрес і блокери → процес завершується тільки після критичних доступів, документів та ознайомлень.

### Offboarding

HR задає дату завершення → система формує checklist і показує об’єкти, які потрібно передати → керівник призначає нових власників задач і документів та нового погоджувача для залежних працівників → IT закриває доступи й сесії → обладнання повернено → HR завершує процес. Критичні пропуски блокують фінальне завершення.

### Документ із повідомлення

У чаті прикріплений файл → `Зберегти у Документи` → вибір компанії/папки в межах прав → toast із посиланням на збережений документ.

## 12. Стани та поведінка

Для кожного списку, картки та drawer обов’язкові:

- loading skeleton, що повторює реальну форму контенту;
- component-level loading: завантаження drawer або tab не перекриває вже готовий список;
- empty state з поясненням і однією доречною дією;
- no-results state із кнопкою скидання фільтрів;
- error state з короткою причиною й повтором;
- partial-data state, якщо частина блоків не завантажилась;
- success toast із можливістю скасування, де це безпечно;
- confirm dialog лише для незворотних або ризикових дій.

Hover, focus, active і disabled мають відрізнятися не тільки кольором. Анімації — 160–220 ms; drawer — до 260 ms. У режимі reduced motion рух замінюється миттєвою зміною стану.

Toast для критичної дії не зникає до завершення читання або явного закриття. Усі server-actions мають pending-state, блокування повторного submit і результат, який можна зіставити з конкретною дією.

Prefetch є непомітною оптимізацією: його помилка не показує toast, доки користувач не відкрив відповідний об’єкт. Background job не використовує нескінченний spinner — показує поточний стан, час останнього оновлення, безпечний retry та можливість залишити сторінку без скасування роботи.

## 13. Адаптивність

### 1280 px і більше

Повний sidebar, 12-колонкова сітка, drawer поверх контенту або з його легким стисканням.

На 1366×768 sidebar за замовчуванням може бути згорнутим, focus-photo переходить у компактний стан, а dashboard показує критичні блоки до першого scroll.

### 1024–1279 px

Sidebar згортається до іконок; dashboard переходить у 8 колонок; другорядні блоки стають нижче; таблиці зберігають ключові колонки.

### 768–1023 px

Навігація відкривається як overlay; drawer займає 55–65% ширини; таблиці переходять у адаптивні рядки; календар за замовчуванням відкриває режим розкладу.

Onboarding показує summary, блокери й найближчі кроки; повний checklist відкривається окремим екраном. Редактор ролей і company-impact операції переходять у read-only preview.

### Менше 768 px

Нижня навігація: `Огляд`, `Задачі`, `Заявки`, `Календар`, `Ще`. Чат доступний у topbar. Головна дія — компактна floating-кнопка. Drawer стає full-screen sheet. На dashboard спочатку показуються `Потребує уваги` та `Сьогодні`, а фото у welcome-блоці приховується або стає маленьким фоновим акцентом.

## 14. Доступність і контент

- контраст тексту та controls — не нижче WCAG AA;
- повна keyboard navigation;
- видимий focus-ring;
- логічний порядок tab-navigation і skip-link до основного контенту;
- focus trap у modal/drawer та повернення focus на елемент, який їх відкрив;
- screen-reader назви для іконок, status dots і кнопок без тексту;
- aria-live або еквівалентне озвучення помилок, toast і результатів async-дій;
- заголовки, списки й таблиці мають коректну семантичну структуру;
- tap target не менше 44×44 px на touch;
- статус не передається лише кольором;
- інтерфейс залишається робочим при zoom 200%;
- критичні hover-дії доступні при keyboard focus;
- фото співробітників мають коректні alt-описи або порожній alt, якщо дублюють ім’я поруч;
- дати подаються у форматі `13 липня, 14:30`, а відносний час — лише як додатковий текст;
- тексти кнопок — дієслова: `Створити задачу`, `Завантажити файл`, `Надіслати запит`;
- уникати технічних повідомлень на кшталт `Error 500` без людського пояснення.

## 17. Критерії приймання дизайну

- за 5 секунд зрозуміло, що потребує уваги користувача сьогодні;
- на кожному екрані є тільки одна візуально головна дія;
- другорядна інформація не займає постійну колонку, якщо потрібна лише епізодично;
- drawer/popover після закриття повертає фокус і не скидає scroll, фільтри, сортування або вибір;
- критичний статус, дедлайн, блокер, конфіденційність і незбережені зміни не ховаються progressive-disclosure патерном;
- інтерфейс не створює вкладених drawers і не змушує проходити більше двох шарів до робочої дії;
- dashboard не виглядає як сітка однакових віджетів;
- ключова сутність відкривається без втрати поточного контексту;
- фільтри та вибране представлення зберігаються після закриття drawer;
- фото допомагають бренду й орієнтації, але не зменшують робочу щільність;
- усі основні операції доступні з клавіатури;
- немає горизонтального scroll на цільових breakpoints, крім спеціально дозволених data tables;
- усі empty/loading/error states спроєктовані;
- nickname login, first-login, admin reset, 2FA, access-help та session-expired не створюють тупикових сценаріїв;
- на login-екрані немає email-поля або вибору компанії/ролі; контактна пошта не приймається замість нікнейма;
- адміністратор може скинути пароль без email, але не може переглянути постійний пароль; тимчасовий пароль видно один раз, а користувач не потрапляє до CRM до його заміни;
- reset пароля відкликає активні сесії, не вимикає 2FA й залишає audit-event без secret;
- нікнейм деактивованого або перейменованого акаунта не перевидається іншій людині;
- credential reset повного адміністратора не виконується однією людиною, якщо доступний другий активний full admin;
- у продукті немає impersonation: permission preview не створює чужу сесію;
- UI не показує дію, яку server-side permission engine забороняє, але безпека не залежить від приховування UI;
- адміністратор без окремого content-права не читає приватний HR/security-контент;
- notification, search snippet, dashboard і export не розкривають заборонених полів;
- повторна відправка рішення не створює дубль задачі, події або audit-record;
- критичні зміни мають re-auth, impact preview і audit відповідно до матриці;
- файл до завершення security-перевірки не доступний іншим користувачам;
- сценарій відновлення з резервної копії перевірено на staging;
- у кожній заявці зрозуміло, хто зараз приймає рішення, який строк і що відбудеться після погодження;
- погоджена відсутність без повторного введення даних з’являється у календарі й privacy-safe статусі присутності працівника;
- приватний HR-коментар заявки на відсутність не доступний керівнику та не потрапляє у notification/search/calendar;
- збій одного автоматичного effect після погодження показується окремо й не створює повторного людського рішення;
- onboarding/offboarding використовує реальні пов’язані задачі, а не декоративний checklist;
- обов’язкове ознайомлення має дедлайн, підтвердження та звіт для відповідального;
- задача, заявка, документ, подія й працівник мають взаємні посилання та спільну timeline;
- адміністратор до збереження бачить diff та кількість користувачів, яких торкнеться зміна прав;
- `Перевірка доступу` показує фактичний результат для конкретного користувача, компанії й об’єкта;
- система не дозволяє випадково видалити останнього повного адміністратора або залишити критичні об’єкти без власника;
- зміни доступів, безпеки та компаній відображаються у зрозумілому журналі дій;
- company-context завжди видимий, коли дані змішані між компаніями, а створення сутності зі scope `Усі доступні` вимагає явного вибору компанії;
- оголошення мають реальні draft/publish/archive states, audience permissions і не перетворюються на другий knowledge-base;
- retention/purge не видаляє records без policy, dependency check, audit і legal-hold check;
- продукт сприймається як єдина система, а не набір сторінок з різних шаблонів;
- візуально це LankaDWS, а не перефарбований Bitrix або копія референсу;
- LCP, INP і CLS відповідають budgets розділу 10.1 на p75 реальних сесій;
- dashboard не завантажує код складної адмінки, charts і editors до переходу у відповідний route;
- list request не повертає comments, audit, повні вкладення або поля невідкритого drawer;
- невідкрита вкладка drawer не створює запит на власні важкі дані;
- повторне відкриття сутності використовує валідний ізольований кеш, але зміна прав відкликає його негайно;
- master-PNG не потрапляє в production delivery без responsive-оптимізації;
- Onest не створює невидимий текст або помітний layout shift під час завантаження;
- export, preview і scan не блокують request-response та мають зрозумілий статус background job;
- critical actions не використовують optimistic completion;
- performance regression понад 10% не проходить реліз без зафіксованого обґрунтування.
- перехід між усіма основними секціями змінює URL, а refresh, Back/Forward і пряме відкриття deep link не гублять дозволений контекст;
- невідомий URL показує branded 404 і не мовчки повертає користувача на Огляд;
- 403 не розкриває існування конфіденційного об’єкта, а 500 не показує stack trace або приватний payload;
- у жодному UI-тексті або mock DTO немає формальної сутності `Команда`, `Підрозділ`, `teamId` чи `departmentId`;
- роль завжди видима біля імені у sticky-профілі sidebar;
- `/admin/*` використовує одну вкладену sidebar-навігацію без дубльованої світлої колонки або top-tabs;
- усі обов’язкові static images фізично існують локально, мають fallback і не містять baked-in UI-тексту.

## 18. Definition of Done для Codex

Робота не вважається завершеною після створення компонентів. Codex має самостійно виконати доступні перевірки та виправити знайдені проблеми.

### Обов’язкова структура реалізації

- кореневий `package.json` використовує npm workspaces; frontend живе в `apps/web`, backend — у `apps/api`, спільні transport types/enums — у `packages/contracts` або в уже погоджених еквівалентних workspace paths;
- frontend не імпортує Prisma Client, NestJS module або server-only environment; shared contract package не містить database/security implementation;
- централізований route config містить path, title, permission і lazy module;
- один app shell і один sidebar-компонент для всіх ролей;
- рольові пункти визначаються permission config, а не трьома незалежними sidebar-макетами;
- shared UI: Button, IconButton, Input, Select, Chip, Avatar, Card, Table/List, Drawer, Modal, Tabs, Accordion, Toast, Skeleton, EmptyState, ErrorState, CompanyContextSelector;
- mock repositories/services відділені від pages; components не імпортують seed arrays напряму;
- entity DTO використовують `companyId`; `teamId` і `departmentId` відсутні;
- date/time utilities працюють із UTC, timezone користувача й календарем компанії;
- static asset manifest дозволяє знайти кожне hero/error/empty/portrait з коду без magic external URL;
- error boundary є на app і route/widget рівнях;
- protected route перевіряє auth і permission до показу сторінки;
- current user/cache скидається при mock logout або зміні demo-user, щоб не показати дані попередньої ролі.

### Автоматизовані перевірки

Ручний перегляд не замінює test suite. У `apps/web` або кореневих npm workspace scripts мають працювати узгоджені команди `lint`, `typecheck`, `test`, `test:e2e` і `build` без hidden interactive prompts.

- unit/component tests — Vitest + Testing Library або вже наявний сумісний стек;
- E2E — Playwright або вже наявний сумісний browser runner;
- accessibility smoke — axe-core/Playwright integration для login, sidebar, primary forms, drawer/modal і error pages;
- route/permission tests покривають direct URL, refresh, Back/Forward, 403/404 і cache reset після зміни demo-user;
- auth tests покривають nickname-only login, first-login, one-time reset, 2FA continuity, reserved username, unlock і two-person admin reset;
- workflow tests покривають absence `v1 → returned → v2 → approved`, idempotent double submit і partial automation error;
- company tests доводять, що selector, URL, create defaults, cache keys і result rows використовують один scope;
- announcement tests покривають audience filtering, scheduled publish, pinned/read state та archive;
- test fixtures не містять production secrets або реальних персональних даних; one-time password у snapshot/screenshot маскується;
- CI або локальна release-команда завершується помилкою при failed test, type error, unresolved asset чи порушенні критичного accessibility rule.

### Візуальна перевірка

- зробити browser screenshots щонайменше для 1440×900, 1366×768, 390×844;
- перевірити чотири рольові `/overview`, а також `/admin`, `/requests`, `/employees`, 403, 404, 500 і offline;
- перевірити `/announcements`, announcement drawer/create, company selector і mixed-company tables;
- перевірити `/login`, `/first-login`, `/access-help` і admin reset-password modal/result на desktop та mobile; live temporary password не потрапляє у збережені screenshots або test artifacts;
- перевірити, що portrait не перекриває текст, кнопки або focus outline;
- перевірити alpha-краї PNG на світлому focus-блоці й відсутність CLS після завантаження;
- порівняти sidebar між ролями: геометрія, логотип, відступи й bottom profile однакові; змінюються лише дозволені items, badges, active state та role label;
- виправити переповнення українського тексту, випадкову англійську локалізацію, обрізані labels і layout shift до передачі результату.

### Фінальна передача

Codex залишає в monorepo актуальні `README.md`, `.env.example` без secret, workspace scripts і короткий API-adapter contract. README містить вимоги до Node/npm, команди install/dev/build/test/e2e, структуру workspaces, demo-mode, спосіб скидання mock state та перелік відомих backend adapter points.

У фінальній відповіді Codex коротко повідомляє:

- які routes і сценарії реалізовано;
- де лежать згенеровані static assets;
- які mock accounts/спосіб перемикання ролей доступні;
- як скинути demo/mock state без ручного очищення випадкових browser keys;
- які build/test/visual checks виконано;
- який data provider активний: для frontend-only — mock і documented API adapter point; для full monorepo — реальний NestJS API у production та явний dev-only mock mode.

Не завершувати відповідь лише словами «готово» без робочого build і перевірених маршрутів.
